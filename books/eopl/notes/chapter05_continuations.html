5.1 续文传递解释器：把剩余计算保存下来

原书 章首及 §5.1，pp.139–155 / PDF 162–178。

第三章把数据上下文表示成环境，第四章再用存储记录随时间变化的内容；第五章问的是另一件事：一个子表达式得到值以后，程序还欠哪些工作？这些工作组成控制上下文。续文（continuation）把它抽象成“接收这个值并完成余下计算”的对象。

先看阶乘。直接递归的 fact(4) 进入 fact(1) 时，还欠乘 2、乘 3、乘 4。尾递归的 fact-iter(1,24) 则只要把后续结果原样返回。代码有没有递归定义，并不能决定运行过程是否需要增长的控制记录；决定因素是调用结果取得后，还要不要做别的工作。

fact(4) = 4 * (3 * (2 * (1 * fact(0))))
fact-iter(4,1) -> (3,4) -> (2,12) -> (1,24) -> (0,24)

尾位置沿用原续文

如果子表达式的值就是整体的值，子表达式使用整体的续文。if 的分支、let 的正文、调用过程的正文都满足这一点；测试式、let 的右端式、运算符和各实参则先产生一个供后续工作使用的中间值，需要适当的等待帧。

这句话要结合求值阶段读：调用过程之前，解释器会用临时帧求运算符和实参；这些已经完成并弹出的帧，不应再作为“过程返回后要回到调用点”的新帧保留下来。尾调用的关键是在进入过程体时仍传同一个 k，而不是保证整个调用表达式求值期间从不临时建立任何帧。

新的接口为 value-of/k(exp,env,k) 和 apply-cont(k,v)。env 告诉解释器名字代表什么；k 告诉它值取得以后继续什么。k 可以表示成单参数闭包，也可以表示成带标签的帧。两种表示的接口规格相同，正好延续第二章的数据抽象方法。

伴读例：把 −(−(44,11),3) 走完

原书 pp.150–151 推演的逐步整理

-(-(44,11),3)
当前动作从栈顶到栈底的待续工作
求整个表达式end
求 −(44,11)等左值后求右式 3；end
求 44等左值后求 11；等左值后求 3；end
44 已得到，改求 11等右值，再用 44 减它；外层帧；end

最大续文大小按原书把 end 也计一个构造器，共 3。等待帧保存的是当时需要的右式和环境；左值取得以后，再用只保存数值的第二阶段帧替换它。这个替换解释了“帧会缩减”，而不仅是画一条不断增长的栈。

let 的 RHS 返回后，在旧环境上扩展绑定，进入正文并交回外层 k；if 的测试返回布尔后，只求被选分支；过程值保存定义环境，但并不保存定义时的调用续文。调用时把当前 k 传给过程体，结果会完成当前调用所在的计算。

阅读注解
控制与数据

环境、闭包、续文各保存什么

环境保存名字的绑定；闭包保存过程正文与定义环境；续文保存某次计算之后要完成的工作。普通过程值可以被调用多次，每次用调用处传来的续文。捕获续文则保存某次具体执行的未来；它与保存过程定义不是同一件事。

空间计量

尾调用不会消灭所有占用

CPS 把原来隐含在宿主栈的待续工作变成对象。递归阶乘仍会建立随输入增长的乘法续文链；迭代阶乘才可把这类工作压缩进累乘器。环境、大整数、输入与已分配对象也占空间，不能把“控制栈有界”改写成“程序总内存恒定”。

习题 5.1 · ★

原题

用过程表示实现本节的续文数据类型。

印刷 p.153 / PDF 176

解答与执行

把每种续文表示成接收一个表达值的过程：它接到值后完成余下计算。空续文返回值并只记录一次结束；其他构造器捕获原来需要保存的表达式、环境或已得的值。

(define (end-cont) (lambda (v) v))
(define (zero1-cont k) (lambda (v) (k (zero? v))))
(define (diff1-cont e2 env k)
  (lambda (v1) (value-of/k e2 env (diff2-cont v1 k))))
(define (diff2-cont v1 k) (lambda (v2) (k (- v1 v2))))
(define (rator-cont rand env k)
  (lambda (p) (value-of/k rand env (rand-cont p k))))
(define (rand-cont p k)
  (lambda (arg) (apply-procedure/k p arg k)))

这里写的是直接值版本的接口等式；完整实现还对数值、布尔和过程作类型检查。chapter05_cps.rkt 的内联模式实际计算嵌套减法得 30，结束计数为 1。let、if 的构造器分别在接值后进入新环境的正文、所选分支；两者都沿用外层 k。

习题 5.2 · ★

原题

用数据结构表示实现本节的续文数据类型。

印刷 p.153 / PDF 176

解答与执行

每个过程闭包改为带标签的记录，字段就是前题 lambda 的自由变量；apply-cont 按标签分派。对于减法，第一帧保存“右式、原环境”，第二帧保存“左值”；对调用则先保存实参式，再保存过程值。

(diff1 e2 env k) + v1  -> eval(e2, env, diff2(v1,k))
(diff2 v1 k)     + v2  -> apply(k, v1-v2)
(rator rand env k)+ p  -> eval(rand, env, rand(p,k))
(rand p k)      + arg -> invoke(p,arg,k)

chapter05.rkt 用帧列表实现同一分派，state 保存当前阶段；过程调用正文获得原 k。两种表示在数值、列表、let、递归过程上逐例比较，结果与唯一结束次数一致。

习题 5.3 · ★

原题

给这个解释器添加 let2。它与 let 相似，但恰好定义两个变量。

印刷 p.153 / PDF 176

解答与执行

两个右端式依次求值，但都在进入 let2 前的环境中。先保存第二个右端式、两个名字和正文；拿到第一个值后继续求第二式，最后一次扩展两个绑定。不能在第二式之前安装第一个新绑定。

let2 x = e1 y = e2 in body
  eval e1 in env
  eval e2 in the same env
  eval body in extend*(x,y ; v1,v2 ; env)

实现归一化成通用多声明 let，用 collect 帧保存未求的式和已得值。let2 a = 7 b = 4 in -(a,b) 返回 3；若外层 x=10，let2 x = 2 y = x in -(y,x) 返回 8。

习题 5.4 · ★

原题

给这个解释器添加 let3。它与 let 相似，但恰好定义三个变量。

印刷 p.153 / PDF 176

解答与执行

在前题的 collect 帧中再保留一个未求右端式即可。每一步都恢复原环境；只有三个值全部取得，才用三个新绑定进入正文。

eval e1 -> collect(e2,e3; []; env)
eval e2 -> collect(e3; [v1]; env)
eval e3 -> enter body with [v1,v2,v3]

let3 a = 7 b = 4 c = 2 in -(-(a,b),c) 返回 1。解析器恰好接收三组声明，未给足或多给一组都不属于 let3 的语法。

习题 5.5 · ★

原题

像习题 3.9那样，给语言添加列表：空表、cons、car、cdr 与 null?。

印刷 p.153 / PDF 176

解答与执行

空表是可立即交给 k 的值。cons 有两个非尾操作数，按减法的两阶段办法先求头再求尾，并检查尾是表；car、cdr、null? 各用一帧等操作数返回。

eval(cons(a,b),env,k) -> eval(a,env,cons1(b,env,k))
apply(cons1(b,env,k),v) -> eval(b,env,cons2(v,k))
apply(cons2(v,k),vs) -> apply(k, cons(v,vs))

空表取 car/cdr 是错误；null? 不能把任意数值当非空表。实现把原语列表放入 collect，仍然逐个尾转移；嵌套列表的值不会被当作待执行语法。

习题 5.6 · ★★

原题

像习题 3.10那样，给语言添加 list 表达式。提示：考虑加入两个新续文构造器，一个负责求列表首元素，一个负责求其余元素。

印刷 p.153 / PDF 176

解答与执行

可定义 list-first(rest,env,k) 和 list-rest(v1,k)：前者接到首值后求剩余表，后者接到其余值表后 cons。空的 list 直接交付空表。这样不会把“求剩余元素”嵌在宿主 cons 的操作数里。通用 collect 版本把已经得到的值逆序暂存，到终点只反转一次；时间线性，帧中的临时值量线性。

list(1,2,3) 返回 (1 2 3)；带打印的元素按左到右执行，不能借用未指定次序的宿主 map 来定义源语言效果顺序。

习题 5.7 · ★★

原题

给解释器添加多声明 let，见习题 3.16；声明数可以任意。

印刷 p.153 / PDF 176

解答与执行

使用一张名字表、一张未求右端式表和一张已得值表。所有右端式在同一个旧环境中从左到右求值；末尾检查名字和值数目相同、名字无重复，再建立正文环境。零声明直接进入正文。

源码 collect/finish 的 let 分支就是完整实现。它与 let* 的区别可用外层 x=10 的例子检验：let x = 2 y = x in -(y,x) 为 8，而顺序安装绑定会错误地得到 0。

习题 5.8 · ★★

原题

给解释器添加多参数过程，见习题 3.21。

印刷 p.153 / PDF 176

解答与执行

先求运算符，再在调用环境求各实参；collect 保留过程值和已经得到的实参。收集结束检查实参数与形参数相同，随后把形参与值同时绑定到闭包保存的定义环境。过程体直接使用调用表达式原来的 k。

invoke(closure(params,body,saved-env), args, k)
  check length(params) = length(args)
  eval(body, extend*(params,args,saved-env), k)

零参数过程也适用。少参数、多参数均产生参数个数异常 1001；重复形参在建立过程时拒绝。代码没有为进入过程体额外保留“返回这一调用”的帧。

习题 5.9 · ★★

原题

把解释器改为实现 IMPLICIT-REFS。提示：考虑新增续文构造器 (set-rhs-cont env var cont)。

印刷 p.153 / PDF 176

解答与执行

环境从名字映射到位置；读变量要解引用，新 let/形参绑定分配新位置。赋值先在原环境求右式，之后找到变量的位置、写入值，并把任取的赋值结果 27 交给原 k。递归组先分配全部位置，再安装捕获同一组环境的闭包。

eval(set x = rhs, env, k)
  -> eval(rhs,env,set-rhs(env,x,k))
apply(set-rhs(env,x,k),v)
  -> store[lookup(env,x)] := v; apply(k,27)

run 的 #:implicit? #t 实现这些规则。let x = 0 in begin set x = 9; x end 返回 9；闭包捕获位置，能看到后来的写入。

习题 5.10 · ★★

原题

修改上一题的解答，使赋值续文不必保存环境。

印刷 p.153 / PDF 176

解答与执行

建立赋值帧时就把 x 查成位置，帧只保存该位置和外层 k。环境在右式求值期间不改变 x 的绑定身份，因此预先查位置与事后查相同；右式可能改变位置的内容，所以不能提前读取其旧值。

eval(set x = rhs,env,k)
  -> eval(rhs,env,set-location(lookup-location(env,x),k))
apply(set-location(loc,k),v) -> store[loc] := v; apply(k,27)

完整机器实际采用这个版本，赋值帧为 (set loc)；右式自己的局部遮蔽不会改掉已保存的目标位置。

习题 5.11 · ★★

原题

给续文传递解释器添加习题 4.4 的 begin 表达式。确保 value-of 或 value-of-rands 的调用都不出现在会增长控制上下文的位置。

印刷 p.153 / PDF 176

解答与执行

对非最后一式建立“继续求剩余序列”的帧，忽略其返回值，但保留效果；最后一式直接用原 k 求值。

eval(begin e1; ...; en end,env,k)
  n=1: eval(e1,env,k)
  n>1: eval(e1,env,begin-frame([e2,...,en],env,k))
apply(begin-frame(rest,env,k),ignored) -> eval(begin rest end,env,k)

源码 begin 分支的转移均为尾调用/状态返回。实际 begin print(1); print(2); 9 end 依次打印 1、2，结果 9；序列必须至少有一式。

习题 5.12 · ★

原题

给图 5.4–5.6 的解释器加上追踪输出，使它产生与 p.150 推演相似的记录。

印刷 p.153 / PDF 176

解答与执行

在 eval、apply、invoke 入口记录阶段、待求表达式、当前值与帧栈；为避免闭包的递归环境无穷打印，环境只记身份或绑定名，帧则展开标签和必要字段。记录不改变控制状态。

#:trace? #t 返回可检查的记录。对嵌套减法，帧依次从空栈到“外层右式 3”、再到“内层右式 11，外层右式 3”；收到 44 后第一帧改为“左值 44”，得到 33 后只剩外层帧，最后将 30 送到空栈。该轨迹与正文表逐步对应。

习题 5.13 · ★

原题

把本章开头的 fact 与 fact-iter 定义译成 LETREC；可以加入乘法。用上一题的追踪解释器计算 (fact 4) 和 (fact-iter 4)，与章首推演比较。在 fact 的轨迹中找出 (* 4 (* 3 (* 2 (fact 1))))；这次 (fact 1) 调用对应的 apply-procedure/k 的续文是什么？

印刷 p.153 / PDF 176

解答与执行

letrec fact(n) = if zero?(n) then 1
                 else *(n,(fact -(n,1)))
in (fact 4)

letrec fact-iter(n,a) = if zero?(n) then a
                      else (fact-iter -(n,1) *(n,a))
in (fact-iter 4 1)

两者实际都返回 24。第一程序进入 fact(1) 的过程体时，续文是“将结果依次乘 2、3、4，再交给 end”；按内层在左的帧栈记为 [mul(2), mul(3), mul(4)]。fact(1) 自己的乘 1 尚未入栈。第二程序尾调时不保留乘法，累乘已经进了 a：(4,1) → (3,4) → (2,12) → (1,24) → (0,24)。

习题 5.15 · ★

原题

本节续文类型只有 end-cont 一个常量，其余构造器恰好各有一个续文参数。把续文实现为列表：end-cont 用空表表示；其他续文用非空表，其 car 是带区别标签的帧（frame，也称 activation record），cdr 是内嵌的续文。观察解释器怎样把它当作帧栈使用。

印刷 p.155 / PDF 178

解答与执行

将 (diff1-cont e env k) 写成 (cons (list 'diff1 e env) k)。应用时取 car 分派、把 cdr 作为外层 k；新帧压栈、完成一项弹栈。机器正采用这个表示。

尾过程调用完成实参收集后直接把已经弹出的 rest 传给过程体；没有额外 return 帧。持久化的列表可以让 letcc 安全保存同一个旧栈：以后 push/pop 只创建新 cons 或改局部指针，不会破坏捕获者看到的节点。

原题

5.2 蹦床解释器：让宿主调用链及时返回

原书 §5.2，pp.155–160 / PDF 178–183。

经过 CPS 后，解释器的主要调用都在尾位置。在支持正确尾调用的 Scheme/Racket 中，它们可以复用宿主控制栈；许多普通过程式实现仍会为每个尾调用压入返回地址。若把相同代码逐行翻译过去，这条调用链可能一直到程序结束都不返回。

蹦床（trampoline）把“立刻继续”改成“先把下一步还给驱动器”。遇到过程应用时返回零参 thunk；驱动器拿到 thunk，调用它获得下一项，再重复。用数据表示则返回一个带 PC、环境、续文和值的快照；最终值用单独的 Done 标签表示。

Bounce = Done(value) | Next(snapshot)
trampoline(bounce):
  while bounce is Next:
    bounce = resume(bounce.snapshot)
  return bounce.value

原书图 5.7 的合同写成 Bounce = ExpVal ∪ (() → Bounce)。expval 必须与宿主 thunk 能可靠区分；定义语言中的过程值不应因为它也代表“过程”，就误被驱动器当作下一步去调用。采用显式标签能把这两个层次分开。

查看实现 · snapshots
(struct state (pc exp env frames value) #:transparent)
(struct thread (id parent state ticks status mailbox) #:mutable #:transparent)
(struct result (value output metrics trace threads) #:transparent)
(define (E e env k) (state 'eval e env k #f))
(define (A k v) (state 'apply #f #f k v))
(define (I p vs env k) (state 'invoke p env k vs))
(define (R k v) (state 'raise #f #f k v))

只在 apply-procedure/k 处切开，已经足以阻止跨无界源过程调用的宿主链；本伴读把 eval/apply/invoke 每个转移都切成状态，控制步长更容易观察。无论切在哪里，记录必须含恢复需要的全部数据；只保存“要调用哪个函数”却漏 env/k，就不是完整快照。

实现的 loop 和 thunk 两种驱动使用同一转移关系，实际比较的不仅是最终 30/24，还包括完整语义轨迹。蹦床改变的是宿主怎样驱动这些状态；源语言的操作数次序、异常目标与词法环境都保持原规定。

阅读注解
两层执行

源程序的尾调用与宿主调用

源程序尾调用可不增加源续文，但实现它的宿主函数仍可能压栈。数据驱动器让宿主每步先返回，再进入下一步，才把两种控制行为分开。这也是为什么只把 value-of 最外层放进循环，却仍在内部递归计算操作数，不能解决问题。

暂停点

快照不是存储的备份

快照保存控制位置和恢复数据。第四章引入的可变存储若是共享的，恢复快照会观察当前内容，不会回到暂停瞬间的旧内容。把暂停误做成整个内存复制，会改变后面的线程通信与捕获续文语义。

习题 5.19 · ★

原题

不把 lambda 包在 apply-procedure/k 的本体外，而改为包在 apply-cont 的本体外。修改相应契约。Bounce 的定义需要改变吗？随后像习题 5.18那样把 Bounce 改用数据结构表示。

印刷 p.160 / PDF 183

解答与执行

Bounce 的集合仍是 ExpVal ∪ (() → Bounce)；value-of/k 和 apply-procedure/k 返回 Bounce，而 apply-cont 更精确地总返回零参 thunk。进入 apply-cont 时先不分派，真正分派由 thunk 在下一轮完成。

(define (apply-cont k v)
  (lambda () (dispatch-cont k v)))
;; data version of the delayed call:
(Continue k v)
resume(Continue(k,v)) = dispatch-cont(k,v)

最后一次 Continue(end,v) 的恢复产生 v。任何递归过程求体和任何操作数接值都会经过 apply-cont，因而能不断把宿主栈交还给驱动器；若语法递归有极深的连续下降，细粒度 state 版本还可在 eval 入口一并切断。

5.3 命令式解释器：寄存器与程序计数器

原书 §5.3，pp.160–171 / PDF 183–194。

CPS 之后，一组过程之间只剩尾调用。这时可以用共享寄存器代替形参：调用前把参数写入 exp/env/cont/val/proc 等寄存器，再进入零参数代码块。零参尾调用的动作只剩“换到那个代码位置”，所以可以用跳转代替。

eval-block -> apply-block -> invoke-block -> eval-block
state = (pc, exp, env, cont, val)

原书 even/odd 例的三种形式——传 x 的互递归、共享 x 的零参互递归、标签与 goto——有相同状态序列。它们都在尾位置进入下一个过程；直接递归 fact 却不能未经 CPS 就这样改，因为它还欠一串乘法。

寄存器赋值必须模拟原调用的“先取得全部实参，再同时绑定”。若先覆盖 x，再用 x 构造保存旧值的续文，旧值就丢了。通常先构造 cont、后改 exp/env 能减少冲突；交换 x/y 的参数仍需要临时变量。字段名也要避开全局寄存器名，否则 cases 的局部绑定会遮蔽寄存器。

查看实现 · register-driver
 (define (continue s)
  (define next (or s (next!)))
  (cond [(not next) (void)]
   [(eq? driver 'thunk)
    (let trampoline ([bounce (lambda () (step next))])
     (define b (bounce))
     (define ns (or b (next!)))
     (when ns (trampoline (lambda () (step ns)))))]
   [else (continue (step next))]))
 (continue initial)

阅读注解
并行绑定

先保全旧值，再覆盖寄存器

原调用 f(y,x) 的两个实参都在旧环境取得；改成 x:=y 后再 y:=x 会把两者都变成旧 y。寄存器化正确性必须逐条检查数据依赖，而不只是把形参名改成全局变量。临时寄存器承担的是原本由宿主调用机制提供的并行绑定。

机器边界

程序计数器并不等于源语法树

PC 是解释器当前执行哪个阶段/标签；exp 则是正在解释的源 AST。一个源调用要经过 EV、AP、INVOKE 多步。把两者混称为“执行到哪行”容易漏掉正在等待的操作数和值，也无法准确解释恢复快照。

5.4 异常：选择另一条完成路径

原书 §5.4，pp.171–178 / PDF 194–201。

普通续文规定一条正常完成路径。异常改变的是：某个值取得后，不再完成当前所有待续工作，而是寻找最近仍有效的处理器。try 安装一个处理器；正常返回时拆掉它；raise 先求出异常值，再沿异常路径转移。

伴读例：同一个 raise，三种完成方式

原异常规则与恢复扩展的对照

try -(10,raise 99) catch(e) 3
try -(10,raise 99) catch(e,k) (k 3)

普通异常语义下，第一式跳过减法，整个 try 的值是 3。恢复型语义让 handler 返回的 3 成为 raise 的值，接着算 10−3，得到 7。第二式把选择权明确交给 handler：它调用 k(3) 时恢复，直接返回 3 时则退出 try。三种路径已分别运行。

数据续文实现把 try 做成特殊帧；raise 从当前栈向外找第一个 try，丢弃它之前的算术、实参和普通等待帧。处理器正文必须用安装 try 时的词法环境，并在异常变量上扩展；它正常返回使用 try 外层的 k，重抛则交给更外层处理器。

查看实现 · exception-unwind

原书 index 例中查不到元素时 raise 99，许多“递归返回后加一”的差值帧被一并跳过，handler 返回 −1。若没有异常，所有待加一都会执行。这使续文不仅是实现细节：它准确说明哪些工作在异常后不再发生。

逐栈搜索可通过每帧缓存最近 try 或显式传正常/异常两个续文避免。两个续文的版本使控制更直接：eval(e,env,k,h)，成功调用 k，异常调用 h；try 只暂时替换 h。过程体接调用时的 h，而闭包保存词法 env，动态处理器与词法数据上下文仍是两套机制。

letcc 再把当前正常续文变成可传递的值；throw 求完值式和目标式后，把值送到捕获点，抛弃即时 k。letcc out in -(1,throw 7 to out) 运行得 7。它恢复控制路径，不回滚已经完成的打印和赋值；保存的帧须保持不可变才能安全重复使用。

阅读注解
处理器作用域

在处理器中重抛要向外走

找到 try 后，handler 在该 try 外面的异常通道执行。若把原 try 又作为最近处理器传进去，handler 的 raise 会被自己接住，造成错误重复甚至循环。恢复型异常还要同时保存恢复点的正常续文和 handler 的外层异常通道。

非局部跳转

值先求完，才改变去向

raise 的参数可以自己计算、输出甚至抛异常；throw 的两个操作数也都在即时上下文求值。只有当这些值取得，才选择新的续文。提前跳转或重复恢复 raise 参数，会更改源程序效果，不能视作同一种实现。

5.5 线程：把多个未完成计算交给调度器

原书 §5.5，pp.179–191 / PDF 202–214。

线程把“一个待完成计算”变成调度器管理的多个对象。本节 THREADS 基于隐式引用；每个线程保有自己的控制状态，所有线程访问同一个 store。任意时刻只有一个 running，ready 队列存可运行线程，mutex 等待队列存 blocked 线程。这里模拟交错执行，不是用多个物理 CPU 同时运行解释器。

spawn 先求过程值，再为子线程建立恢复记录并放在 ready 队尾。原书父线程取得任取的 73，子过程接任取的 28；线程 ID 习题改为父子都取得新子 ID。主线程结束时保存 final-answer，子线程结束时只丢弃其返回值；两者都继续运行 ready 队列里的线程。

抢占点放在 apply-cont 入口：时间片未尽，先减剩余步再分派；已经为零，就保存“仍待执行这个 apply”的快照，放回队尾并换线程。时间片计的是续文应用次数，不是源语句条数或真实毫秒。yield 主动交出 CPU 时，恢复点应是把 99 交给原 k。

共享计数器的 set x = -(x,-1) 不是单个原子更新：读 x 与最后写回之间可能抢占。两个线程都读到 0，各自计算 1 并写回，便丢了一次增加。mutex 把这段读—改—写包在临界区里；但主线程若不等待子线程，最后返回的也可能是过早的 x。互斥和等待完成各自解决一个问题。

原书 mutex 允许任意线程 signal：开放时 wait 关闭它并继续；关闭时 wait 排队；signal 有等待者时把最前者送入 ready，mutex 仍保持关闭，等于直接把许可交给那位等待者。若这时错误地开放，新来的线程就可能抢在已唤醒者之前进入。

本伴读把死锁状态保留在结果中：主线程已经返回 77，而两个子线程互相等待时，最终 ready 为空仍不代表线程池正常完成。消息模型进一步把共享写入改成单一 owner 接收消息；它可以免去部分锁，但消息队列、协议终止和阻塞接收仍须定义。

阅读注解
调度原子性

检查、入队与唤醒是一件事

wait 检查锁状态并把当前恢复点挂到等待队列，必须在一个解释器原子动作中完成；receive 检查 mailbox 和登记阻塞同理。若把它们拆开并在中间允许切换，signal/send 可能落在缝隙里，留下永远等不到通知的线程。

返回与终止

主线程答案不能证明线程池完成

原书 run-next-thread 在 ready 为空时返回 final-answer；它不自动扫描所有 mutex 队列。伴读结果同时给 blocked 数量，主线程没有答案而仅剩阻塞者时报错。读者检查并发程序时要分别判断互斥、结果已可读、所有参与者完成以及是否有等待环。

yield() 已加入解析和机器；恢复点不能是 yield 表达式本身，否则会不断再次让出，永远无法进入后续程序。就绪队列也不能同时保留两个同 ID 的快照。

习题 5.46 · ★★

原题

在上一题中，时间片耗尽与主动 yield 都会把线程放回就绪队列。主动 yield 的线程恢复时却获得完整时间片。修改队列，让它保存线程剩余的时间片（如果还有），恢复时只给它剩余时间。

印刷 p.189 / PDF 212

解答与执行

队列项改成 (snapshot,remaining)。主动 yield 保留当前剩余值；真正耗尽时间片时，入队前把 next remaining 重置为 quantum；取队时使用项内值。

#:preserve-ticks? #t 实现这一差别。若 yield 时已经为 0，不能反复恢复一个永远无步可走的线程：本实现让下一次 apply 检出 0，把它作为“已耗尽”重排并补足新片。q=1 下也实际正常结束。公平性依赖轮转队列和每个动作最终让出，不能从保存余额本身推出。

习题 5.47 · ★

原题

如果最后剩下两个子线程，各自等待另一个子线程持有的 mutex，会怎样？

印刷 p.189 / PDF 212

解答与执行

它们形成等待环，两个都 blocked，没有 ready 线程。原书调度器只检查 ready 是否空，因此会返回主线程保存的 final-answer，即使子线程仍死锁；若主线程也未完成，它甚至可能返回未初始化值。这不是所有线程完成的证明。

运行例中两个子线程各获取 a/b，yield 后等待对方，主线程返回 77；机器保留结果 77，同时报告 blocked=2。若死锁阻止主线程产生答案，伴读实现明确报 deadlock before main result。更严格的运行器可把任何非空阻塞集合都判作失败，这是单独的终止策略。

习题 5.48 · ★

原题

本节用过程表示线程。改用数据结构表示。

印刷 p.189 / PDF 212

解答与执行

线程记录保存 id,parent,state,ticks,status,mailbox，其中 state 是 EV/AP/INVOKE 之一。新子线程的 state 为“以 end-sub 调用过程”；被抢占线程的 state 为“以原 k 再次应用当前 v”；等待 mutex 的线程保存“取得锁后返回 52”的 AP 状态。

习题 5.49 · ★

原题

对 THREADS 完成习题 5.15：把续文表示为帧栈。

印刷 p.189 / PDF 212

解答与执行

普通运算仍为同一持久帧栈，补上 spawn、wait、signal、print、set 等一元帧；结束用线程记录的 ID 区分：主线程空栈时保存 final-answer，子线程空栈时只结束并选择下一线程。

习题 5.50 · ★★

原题

把本节解释器寄存器化。哪些互相尾递归的过程必须一起寄存器化？

印刷 p.189 / PDF 212

解答与执行

核心集合包括 value-of/k、apply-cont、apply-procedure/k、run-next-thread、wait-for-mutex 和 signal-mutex；若实现分出 thread-resume 或 apply-handler，且它们与核心互相尾调，也要一起纳入。enqueue、newref 等有限返回的辅助过程无需因此寄存器化。

习题 5.51 · ★★★

原题

希望图 5.17 的消费者不必忙等，而是在生产者把值放入缓冲区后被唤醒。用 mutex 写出这样的程序，或者实现允许这种行为的同步算子。

印刷 p.189 / PDF 212

解答与执行

对一次生产、一次消费，用一个事先关闭的 ready mutex 作为一次通知即可；生产者写完 buffer 才 signal，消费者 wait 后才读。

let buffer = 0 in let ready = mutex()
in begin
     wait(ready);
     spawn(proc(d) begin set buffer = 44; signal(ready) end);
     wait(ready);
     buffer
   end

ready 最初被主线程关闭，因而生产者先运行或消费者先 wait 都不会丢通知：先 signal 会把它打开，后 signal 会把锁直接移交等待者。这个一次性程序实际返回 44，无忙等循环。多次生产消费需要两个计数信号量或条件变量和谓词循环，不能让单个 binary mutex 记住任意多个尚未消费的通知。

习题 5.52 · ★★★

原题

用 mutex 写一个类似图 5.21 的程序，不过主线程须等三个子线程全部结束后再返回 x。

印刷 p.189 / PDF 212

解答与执行

给三个子线程各设一个 initially-closed 的 done mutex。子线程在共享 mut 保护下加一，退出临界区后 signal 自己的 done；主线程 wait 完三个 done，再读 x。

查看推演代码
let x = 0 in let mut = mutex()
in let a = mutex() b = mutex() c = mutex()
in let worker = proc(done)
     begin wait(mut); set x = -(x,-1); signal(mut); signal(done) end
in begin
     wait(a); wait(b); wait(c);
     spawn(proc(d)(worker a));
     spawn(proc(d)(worker b));
     spawn(proc(d)(worker c));
     wait(a); wait(b); wait(c);
     x
   end

这里用的是原书允许跨线程 signal 的 binary semaphore 语义；不是要求只有加锁者可解锁的操作系统 owner mutex。q=1…30 已逐次执行，全部返回 3、blocked=0；主线程最后读取的位置确实在三次更新之后。

习题 5.54 · ★★

原题

给上一题的解释器添加 kill。给定线程号，在就绪队列或任何等待队列中找到它并移除。找到返回真；所有队列中都没有这个线程号则返回假。

习题 5.55 · ★★

原题

let p = self()
in let c = spawn(proc(id) send(p,-(id,-40)))
   in receive()

#!/usr/bin/env python3
"""Executable scheduler models for 5.56/5.57. Commands are yielded snapshots,
not a second parser for THREADS. Messages contain JSON-like immutable data.
"""
from collections import deque
from copy import deepcopy
from dataclasses import dataclass, field
import json

@dataclass
class Semaphore:
    count: int
    waiting: deque = field(default_factory=deque)

@dataclass
class Condition:
    waiting: deque = field(default_factory=deque)

@dataclass
class Barrier:
    parties: int
    generation: int = 0
    waiting: list = field(default_factory=list)

@dataclass
class Task:
    ident: int
    continuation: object
    store: dict = field(default_factory=dict)
    mailbox: deque = field(default_factory=deque)
    pending: object = None
    status: str = "new"

class Scheduler:
    def __init__(self):
        self.tasks, self.ready, self.output = {}, deque(), []

    def add(self, program):
        ident = len(self.tasks)
        task = Task(ident, None)
        task.continuation = program(task)  # task.store is private to this thread
        self.tasks[ident] = task
        self.wake(task)
        return ident

    def wake(self, task, value=None):
        assert task.status != "ready"
        task.pending, task.status = value, "ready"
        self.ready.append(task)
        assert len({t.ident for t in self.ready}) == len(self.ready)

    def up(self, sem):
        if sem.waiting:
            self.wake(sem.waiting.popleft())  # direct handoff, no spare permit
        else:
            sem.count += 1

    def down(self, sem, task):
        if sem.count:
            sem.count -= 1
            self.wake(task)
        else:
            task.status = "semaphore"
            sem.waiting.append(task)

    def run(self, fuel=10000):
        steps = 0
        while self.ready:
            steps += 1
            if steps > fuel:
                raise RuntimeError("fuel exhausted")
            task = self.ready.popleft()
            task.status = "running"
            try:
                action = task.continuation.send(task.pending)
            except StopIteration:
                task.status = "done"
                continue
            op, *args = action
            if op == "down":
                self.down(args[0], task)
            elif op == "up":
                self.up(args[0]); self.wake(task)
            elif op == "condition-wait":
                condition, lock = args
                condition.waiting.append(task)
                task.status = "condition"
                self.up(lock)  # enqueue+release is one atomic scheduler operation
            elif op == "condition-signal":
                if args[0].waiting:
                    self.wake(args[0].waiting.popleft())
                self.wake(task)
            elif op == "barrier":
                barrier = args[0]
                barrier.waiting.append(task); task.status = "barrier"
                if len(barrier.waiting) == barrier.parties:
                    waiting, barrier.waiting = barrier.waiting, []
                    barrier.generation += 1
                    for waiter in waiting:
                        self.wake(waiter, barrier.generation)
            elif op == "send":
                dest, value = args
                receiver = self.tasks[dest]
                # This model restricts messages to JSON data, never references/closures.
                copied = json.loads(json.dumps(value))
                if receiver.status == "receive":
                    self.wake(receiver, copied)
                else:
                    receiver.mailbox.append(copied)
                self.wake(task)
            elif op == "receive":
                if task.mailbox:
                    self.wake(task, task.mailbox.popleft())
                else:
                    task.status = "receive"
            elif op == "print":
                self.output.append(args[0]); self.wake(task)
            else:
                raise ValueError(op)
        return {t.ident: t.status for t in self.tasks.values()}
