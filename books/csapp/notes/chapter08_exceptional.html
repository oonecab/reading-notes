8.1 · 先确定事件、入口和返回位置Exceptions

来源：印刷 759—767 页 / PDF 760—768 页

原书摘录 · 异常由事件触发

An exception is an abrupt change in the control flow in response to some change in the processor’s state.

中文释义：处理器状态中的事件使控制流突然改变。这里的 exception 包含硬件中断，不等同于 C++ 的 throw。

来源：印刷 759 页 / PDF 760 页

前几章把程序看作按跳转、调用和返回前进的指令序列。现在设想一条读内存指令遇到不在物理内存中的页：它不能靠普通分支预先检查所有可能事件。硬件必须把控制交给内核，内核补齐页，再让原指令重试。这个“离开—处理—恢复”的路径，就是本章和下一章的连接点。

8.1.1 · 硬件入口与软件处理如何分工Exception Handling

启动时内核建立异常入口，硬件检测事件并取得异常号，保存足以恢复执行的状态，切换到受保护的入口。处理程序识别原因、改变内核状态，再通过专门的异常返回机制恢复程序。保存的不只是普通函数调用的返回地址，还包括状态寄存器、权限及必要的栈信息；来自用户态的异常不能信任用户自己提供的内核栈。

原书图 8.2—8.3 用“基址 + 异常号 × 8”说明地址表索引，是概念模型。真实 x86-64 IDT 使用描述符，syscall 还有专用的入口寄存器机制，不能把每种硬件入口都实现成一本书画的普通函数指针数组。

8.1.2 · 最关键的问题是返回哪条指令Classes of Exceptions

类别触发关系例子处理后控制流
interrupt 中断异步于当前指令设备完成、时钟恢复中断边界后的指令
trap 陷阱指令有意触发系统调用通常下一条；退出类调用不返回
fault 故障当前指令触发，可修复缺页修复后重试当前指令；否则终止
abort 终止类异常不可恢复硬件一致性错误不恢复应用执行

为什么缺页不能直接跳到下一条？假设 movq (%rdi),%rax 还没有取得数据就缺页，跳过它会让后续指令使用旧的 %rax。修复页表后重新执行同一条指令，才能让“程序看起来只执行了一次成功的 load”成立。相反，write 系统调用已经完成服务，返回时继续下一条，才不会重复写出内容。

8.1.3 · 区分 ISA 故障、内核策略和系统调用 ABIExceptions in Linux/x86-64 Systems

x86-64 的除法错误向量是 0、一般保护是 13、缺页是 14、机器检查是 18。内核如何把它们变成用户可见结果属于另一层：例如整数除零也可能表现为 SIGFPE，名称中的“浮点”不代表只发生于浮点。写只读页或访问未映射地址常由页故障路径最终生成 SIGSEGV；原书把这类访问笼统列入一般保护故障，不能据 SIGSEGV 倒推出一定发生向量 13。

Linux x86-64 原始 syscall 用 %rax 放调用号，前六个参数依次放 %rdi、%rsi、%rdx、%r10、%r8、%r9，返回值在 %rax，%rcx 和 %r11 被破坏。它与普通 System V 函数调用的第四参数寄存器 %rcx 不同。write=1、exit=60 是这个 ABI 的编号；macOS ARM64 不使用这套编号。libc 包装器通常把原始负错误码转换成返回 −1 并设置 errno。

/* Linux x86-64 原始入口示意；不是本机可移植 C 接口。 */
movq $1, %rax      # write
movq $1, %rdi      # stdout
leaq message(%rip), %rsi
movq $13, %rdx     # "hello, world\n" 共 13 字节
syscall

原书的字符串 hello, world 后接换行，共 13 字节，不含结尾 NUL。图 8.11 用 string_end−string 求实际长度，避免手工计数；write 不会自行查找 NUL。

推理

缺页指令尚未完成目标内存访问；修复后重试保持程序语义。

边界

一次系统调用可以在同一进程上下文完成后直接返回，也可以阻塞并切换。

8.2 · 用上下文维持独立执行的表象Processes

来源：印刷 768—773 页 / PDF 769—774 页

原书摘录 · 进程的经典定义

The classic definition of a process is an instance of a program in execution.

中文释义：进程是程序的一次执行实例；可执行文件是程序，执行中的上下文才是进程。

来源：印刷 768 页 / PDF 769 页

8.2.1 · 把自己的 PC 序列从全机执行中抽出来Logical Control Flow

单核依次执行 A 的一段、B 的一段，再恢复 A。A 能继续，是因为内核保存了寄存器、PC、栈等上下文，恢复时这些值接上原来的序列。A 的逻辑控制流可以忽略“中间 B 做了什么”，但墙上时钟会体现 A 被抢占的时间。此抽象并不承诺指令耗时固定。

8.2.2 · 时间重叠是并发，同时用核才是并行Concurrent Flows

A 在 1—3 运行、B 在 2—5 运行、C 在 4—6 运行：A/B 与 B/C 的生命周期重叠，A/C 不重叠。单核交替执行也满足并发；只有不同执行资源上同时运行才叫并行。由此也能看出“与同一个进程并发”不是传递关系。区间端点仅相接时，不把零长度交点视为一段重叠执行。

8.2.3 · 相同虚拟地址不必指向同一字节Private Address Space

父进程 fork 后的 x 和子进程的 x 可以有相同虚拟地址及初值，却属于两个私有地址空间。操作系统可用写时复制延迟真实拷贝，但对程序暴露的私有写入语义不变。显式共享映射和共享的内核打开文件描述是例外，不能从“地址空间私有”推出所有资源都隔离。

图 8.13 的 0x400000 是书中非 PIE 可执行文件布局实例；启用 PIE/ASLR 后代码起址可变。图示 248 和标注 %esp 也不能当作所有 x86-64 进程的固定上界与栈寄存器；此处讨论 64 位栈时应看 %rsp。具体地址与隔离策略由 ABI 和当前内核实现决定。

8.2.4 · 权限限制使地址空间承诺可信User and Kernel Modes

普通应用不能改页表、任意停止处理器或直接读内核敏感状态。系统调用通过预先受控的入口进入内核，内核校验参数后执行服务；并不是应用把一个普通变量置为“内核模式”。Linux 的 /proc 导出的是内核主动提供的接口，也不能据此任意绕过权限。

8.2.5 · 先换执行模式，再可能换进程Context Switches

时刻CPU 正在替谁做什么发生的改变
t0A 用户代码调用 readA → A 的内核路径
t1A 的数据尚未就绪保存 A；恢复 B 的上下文
t2B 用户代码运行同一物理 CPU 执行 B 的逻辑流
t3设备完成，进入内核更新等待状态，A 变为可运行
t4调度选择 A恢复 A，从 read 返回继续

设备完成不意味着 CPU 必须立刻恢复 A；调度器还要决定何时运行它。原书 p773 有“内核代表 A 执行用户态指令”的措辞，准确的分层是应用代码在用户态执行、内核代码在内核态代表当前进程执行。系统调用期间仍然有当前进程，不能另造一个“所有系统调用共享的内核进程”来解释。

8.3 · 让返回值决定后续路径System Call Error Handling

来源：印刷 773—774 页 / PDF 774—775 页

系统级编程的难点常在失败分支。fork 可能因资源限制返回 −1，此时没有子进程；把 −1 当“父进程路径”继续 wait 或 kill，会改变程序含义。waitpid 返回 −1 且 errno=EINTR 表示等待被打断，通常应继续等同一个目标；errno=ECHILD 则表示不存在可等待的匹配子进程，不能一律重试。

原书摘录 · 先查返回值

Programmers should always check for errors, but unfortunately, many skip error checking because it bloats the code and makes it harder to read.

中文释义：应检查系统接口的失败结果；封装应帮助保持可读性，而不是掩盖失败。

来源：印刷 773 页 / PDF 774 页

pid_t r;
int status;
do {
    r = waitpid(child, &status, 0);
} while (r < 0 && errno == EINTR);
if (r < 0) { /* 这里才报告真正的等待失败 */
    perror("waitpid");
    return 1;
}

errno 只有在返回值指出失败时才解释；一次成功调用不保证把旧 errno 清零。书中 Fork、Waitpid 等首字母大写名称是作者的错误包装器，不是 POSIX 函数。包装器若选择终止程序，应使用失败退出码；原书示例 unix_error 调 exit(0) 会把错误报告为成功，本页可运行程序改为非零。能够恢复的错误不能被一个“遇错退出”包装器统一吞掉。

可以把返回值当成“这次是否成功”的标签，errno 当成“失败原因”的附加信息。若早先失败留下 errno=EINTR，后来 waitpid 已成功返回孩子 PID，旧 errno 仍可能是 EINTR；此时应该处理刚领取的状态，不能因为旧错误码再等一次。只有先看到返回 −1，才有理由用 errno 决定重试或报错。

阅读注解
实践

先保住错误码

信号处理程序调用可能改 errno 的函数时，入口保存、返回前恢复。

语义

重试有条件

EINTR 常可重试；坏描述符、无子进程、参数错误需要不同处理。

8.4 · 从复制进程到运行另一份程序Process Control

来源：印刷 774—792 页 / PDF 775—793 页

8.4.1 · PID 标识一次正在管理的执行Obtaining Process IDs

getpid 取得当前进程 ID，getppid 取得当前父进程 ID。父亲退出后父关系可能变化，PID 在旧进程彻底退出后还可能重用，因此缓存一个 PID 不构成永久身份认证。页面的实验只对自己刚创建且尚未回收的子进程发信号。

8.4.2 · fork 在两个地址空间各继续一次Creating and Terminating Processes

设 x=9，执行 pid=fork()。父返回子 PID，子返回 0；两边都从 fork 后一条语句继续，且各有 x=9。子做 x-- 只把自己的副本变成 8；父的 x 仍为 9。一次源码调用可以有两次返回，但失败时仅在父返回 −1。

接口上下文结果返回行为
fork产生新的子进程，程序映像初始相同父得 PID，子得 0，失败得 −1
execve替换当前进程的程序映像，PID 保留成功不回到旧程序；失败 −1
exit / 从 main 返回执行正常结束处理，刷新 stdio不返回
_exit / _Exit直接结束进程，不刷新用户态 stdio不返回

运行、停止、终止是本章的用户视角：运行包括等待 CPU，停止要经 SIGCONT 才能恢复，终止不能恢复。等待 I/O 的阻塞状态与作业控制的停止状态不要混用。fork 前 stdio 未刷新的输出缓冲也会被复制；若父子随后都 exit，一份已经缓冲的文本可被刷两次。为了让题目中的 printf 顶点代表一次可见输出，下文输出排序采用原书的终端行缓冲或显式 fflush 假设。

fork 的返回值为什么能分出两条路径

设原进程 PID 为 100，新孩子 PID 为 101。调用前只有 PID 100 执行 fork()；成功后，PID 100 中赋给 pid 的是 101，PID 101 中赋给 pid 的是 0。因此 if(pid==0) 只有孩子进入，else 的父分支拿着 101 才能精确等待孩子。不是父先得到 101、随后在同一变量里又得到 0；两次返回发生在两个进程各自的执行流中。

8.4.3 · 退出状态是一份必须领取的记录Reaping Child Processes

子进程结束后内核保留 PID、退出原因等信息，等待父进程 waitpid 领取；这段时期是僵尸状态。waitpid(p,&s,0) 精确等待 p，waitpid(-1,&s,0) 等任意子进程。领取退出状态才完成回收；父先调用 wait 并不要求子先结束，内核会让父等待。孤儿由系统指定的收养者处理，Linux 也可能由 subreaper 收养，不能把现代所有情况都固定为 PID 1。

检查宏何时解释含义
WIFEXITED(s)waitpid 返回已结束子进程正常返回或 exit
WEXITSTATUS(s)仅当 WIFEXITED 真退出码低 8 位
WIFSIGNALED / WTERMSIG信号终止时结束原因的信号编号
WIFSTOPPED / WSTOPSIGWUNTRACED 报告停止时进程仍存在，可继续
WIFCONTINUEDWCONTINUED 报告继续时停止进程已恢复

WNOHANG 返回 0 表示当前没有符合条件的状态变化；它不是 PID 0，也不表示所有子进程都没了。回收多个已退出子进程必须循环。若要依创建次序等待，使用有界 for(i=0;i<N;i++)；原书图 8.19 的 while(waitpid(pid[i++],...)) 在最后一个孩子之后仍读 pid[N]，越界，不能照抄。

8.4.4 · 等待时间与等待条件分开Putting Processes to Sleep

sleep(secs) 完整睡完返回 0，被信号打断时返回尚未睡完的秒数。secs−remaining 是整数秒接口所表达的时长，不能精确代表纳秒墙钟时间。pause 只等待下一个可处理信号，不检测业务条件；若条件已经成立后才 pause，就会丢掉唤醒机会。这个缺口将在 8.5.7 用原子换掩码并睡眠解决。

8.4.5 · execve 替换内容，保留进程身份Loading and Running Programs

execve(path,argv,envp) 要求 argv 和 envp 都是以空指针结束的指针数组，每个非空元素指向以 NUL 结束的字符串。argv[0] 按惯例是程序名，环境字符串形如 NAME=value。成功后旧的栈、堆、数据和代码映像被新程序替代，入口启动代码建立新环境后进入 main。

char *const argv[] = {"sh", "-c", "exit 7", NULL};
char *const envp[] = {"PATH=/usr/bin:/bin", NULL};
execve("/bin/sh", argv, envp);
/* 只有失败才到这里；在 fork 的子分支中不要返回 shell 主循环。 */
_exit(127);

execve 不会按 PATH 查找文件；需要搜索时才选择 execvp 一类接口。未设置 close-on-exec 的描述符可继续存在；已捕获信号的处理动作在 exec 后重置，信号掩码却会继承。getenv 返回 value 指针或 NULL；setenv 与现代 POSIX unsetenv 都以 0/−1 返回成功/失败，原书 p788 的 void unsetenv 是旧式原型。

8.4.6 · shell 负责创建、登记、等待与回收Using fork and execve to Run Programs

shell 读一行，区分内建命令与可执行文件。内建 cd 一类操作必须影响 shell 自身；普通命令则 fork，在子进程 exec。父进程保留自己的命令循环，前台时等待，后台时继续读输入。先 fork 再 exec 也为子进程在装入前设置进程组、重定向描述符提供机会。

原书的第一版 shell 故意没有回收后台孩子，因此长期运行会积累僵尸。完整实现还要保证“登记作业”先于“回收后删除作业”，并把 Ctrl+C/ Ctrl+Z 转发给前台作业的整个进程组。本页 作业控制程序采用题目给出的简化终端模型，并在退出时回收自己创建的作业。

推导

用偏序代替猜运行顺序

同一进程语句和 wait 的依赖构成有向边；合法输出是这些边允许的线性排列。

校注

8.5 · 把通知与可靠状态分开Signals

来源：印刷 792—817 页 / PDF 793—818 页

信号把内核或别的进程检测到的事件带到用户级。它与异常处理的关系是“异常先进入内核，内核可能决定通知用户进程”，不是硬件直接执行用户提供的 handler。SIGCHLD 尤其适合通知“孩子状态值得检查了”，但不携带“这次恰好死了几个孩子”的可靠计数。

8.5.1 · 发送、待处理、接收是三个阶段Signal Terminology

发送把通知记入目标的待处理状态；接收才使进程执行默认动作或处理程序。blocked 表示暂时不能接收的类型，pending 表示已经到达但尚未处理的类型。书中把普通信号画成位向量：ready = pending & ~blocked。信号被阻塞仍可变为 pending，解除阻塞也不是“再发送一次”。

原书摘录 · 通知表达至少一次

The key idea is that the existence of a pending signal merely indicates that at least one signal has arrived.

中文释义：一个待处理普通信号只说明至少发生过一次，不能据此恢复次数。

来源：印刷 806 页 / PDF 807 页

本章的单个 pending 位模型适用于所讨论的普通信号；实时信号及排队接口需要另论。即便在普通信号平台上观察到五次发送被合并成一次处理，也只是该实现与这段受控时序的观察。健壮程序从 waitpid 或自己的队列读取工作，而不是依赖“发送数 = handler 次数”。

pending 位可想成一张“有事待查”的便签：第一次到达把 0 改为 1，尚未取走时再来一次，便签仍只有一个 1；它没有空间记录来了两次。孩子的退出记录则分别保存在内核中，三个孩子就是三份可领取状态。因此一次 SIGCHLD 足以提醒主流程循环回收三个孩子，但仅把 handler 次数加一永远不能还原三个退出事件。

8.5.2 · 进程组才是一个作业的信号边界Sending Signals

每个进程属于一个进程组。fork 默认继承组，setpgid(0,0) 让自己成为新组的组长。kill(p,sig) 的 p>0 针对一个 PID，p=0 针对调用者的组，p<−1 针对组 −p；p=−1 有特别的广泛发送语义，不能概括成“组 1”。

一个前台管道可能有多个成员，Ctrl+C 要影响整个前台作业，所以 shell 不能只杀一个 PID。真实终端把键盘信号直接送给终端前台进程组；本章作业控制题采用 shell 收到后再转发的教学模型。alarm(secs) 则安排给自己发送 SIGALRM；同一进程的新 alarm 会替换旧计时，库函数不可随意占用调用者已有的计时器。

8.5.3 · 默认动作与自定义动作不是同一层Receiving Signals

常见动作是终止、终止并可能生成 core、停止、忽略。SIGKILL 与 SIGSTOP 不能捕获、忽略或屏蔽。handler 在本进程的用户态运行，共享本进程全局变量；另一个未被阻塞的信号可以嵌套打断它。默认忽略 SIGCHLD 不表示不需要 wait；显式设置 SIG_IGN 或 SA_NOCLDWAIT 在 POSIX 语义下会改变僵尸处理，不应与默认动作混为一谈。

本页使用 sigaction 明确设置处理函数、处理期间额外掩码和标志。SA_RESTART 只对规定可重启的阻塞操作有效；sleep、sigsuspend 等仍有自己的中断契约，因此错误处理不能靠设置一个标志后全部省略。

8.5.5 · 安全、完整、可移植要同时满足Writing Signal Handlers

最易推理的 handler 只写一个 volatile sig_atomic_t 标志。volatile 使异步改变对当前执行流可见，sig_atomic_t 保证单次访问的适当原子性；它们不把 x++ 变成多线程原子操作，也不保护整个数据结构。一份链表若在“已更新前指针、未更新后指针”时被 handler 遍历，单个字段再原子也没有用。

8.5.7 · 检查条件与睡眠必须接成原子边界Explicitly Waiting for Signals

设 done 初值 0。错误写法 while(!done) pause() 可能先读到 0，随即 handler 把 done 改成 1，再执行 pause；已经没有新信号，程序永睡。换成短 sleep 只让错误变成延迟轮询，并未建立可靠的同步边。

下面以单线程中等待一次 SIGCHLD 通知为例：先安装 handler，并由它把 volatile sig_atomic_t done 置为 1；done 在受保护的准备阶段开始前为 0。SIGCHLD 只通知状态可能改变，孩子是否退出及其状态仍需用 waitpid 读取。示意代码突出掩码关系，完整程序另检查各接口的失败路径。

sigset_t block, old, waiting;
sigemptyset(&block);
sigaddset(&block, SIGCHLD);
sigprocmask(SIG_BLOCK, &block, &old);
waiting = old;
sigdelset(&waiting, SIGCHLD);
/* fork/register 或其他准备；done 只由已安装的 handler 更新。 */
while (!done)
    sigsuspend(&waiting);
/* handler 返回后恢复含 SIGCHLD 的保护掩码，再检查 done。 */
sigprocmask(SIG_SETMASK, &old, NULL);

old 保存调用者原来的掩码；waiting 从 old 复制，再显式删除 SIGCHLD。即使调用者进来时已屏蔽 SIGCHLD，等待期间也能递交该通知，而调用者原先对其他信号的屏蔽保持不变。handler 返回后，恢复的是进入 sigsuspend 前的保护掩码，即 old ∪ {SIGCHLD}；因此检查 done 时仍受保护。循环结束后再恢复 old，把控制权和原来的信号环境一起还给调用者。

sigsuspend 原子地用参数替换当前掩码并挂起；待处理通知会在这个边界得到处理，handler 返回后恢复调用前掩码。循环仍必要，因为唤醒可能来自别的信号。原书 p817 的等价伪码把第一步写成 SIG_BLOCK，若原先已阻塞 SIGCHLD 就无法解除它，正确概念应是 SIG_SETMASK；三条独立调用也不具备 sigsuspend 的原子性。POSIX 的 sigsuspend 定义明确规定替换与恢复。

保护后只剩两类可行时序：如果孩子在父检查之前已退出，SIGCHLD 因被屏蔽而保持待处理，父进入 sigsuspend 的原子边界时就能接收它；如果孩子在父已经挂起后才退出，新信号会唤醒父。关键是不存在“已经允许递交、但还没开始可被唤醒的等待”这一空隙。handler 返回后重新检查条件，既处理无关信号，也让业务状态决定是否结束等待。

main 调 setjmp 保存环境，第一次返回 0，于是调用 outer，再由 outer 调 inner。inner 检测错误后 longjmp(env,2)，outer 和 inner 都不正常返回，执行直接恢复到原先 setjmp 的分支位置，这次观察到 2。longjmp 自身没有正常返回；若传 0，setjmp 一侧得到的是 1。它不是重新从 main 第一条指令运行，也不是倒转内存里所有修改。

case 2: /* inner 使用 longjmp(env, 2) 到这里 */ break;
default: /* 其他错误 */ break;

C 对 setjmp 的出现位置有特别限制；把它用于 switch 的控制表达式或指定的 if/循环条件形式是惯用安全写法，不要随意写成赋值子表达式。保存环境的函数已经返回后，jmp_buf 即使还在堆里也不能作为返回目标。发生跳转后，保存环境的函数中那些在 setjmp 后改变、且未声明 volatile 的自动局部变量值可能不确定；不要把它们当错误现场快照。

/* Single-threaded POSIX experiment. No handler prints or edits a job table. */
static volatile sig_atomic_t noticed;
static volatile sig_atomic_t usr1_count;
static volatile sig_atomic_t expired;
static jmp_buf escape;
static void handler(int sig) {
    int saved = errno;
    if (sig == SIGALRM) expired = 1;
    else {
        noticed = 1;
        if (sig == SIGUSR1) ++usr1_count; /* Same signal is blocked in its handler. */
    }
    errno = saved;
}
static void die(const char *s) { perror(s); exit(1); }
static int reap(pid_t p) {
    int status;
    while (waitpid(p, &status, 0) < 0) {
        if (errno != EINTR) die("waitpid");
    }
    return status;
}
static void install(int sig) {
    struct sigaction sa;
    memset(&sa, 0, sizeof sa);
    sa.sa_handler = handler;
    if (sigemptyset(&sa.sa_mask) || sigaction(sig, &sa, NULL)) die("sigaction");
}
static void inner(void) { longjmp(escape, 2); }
static void outer(void) { inner(); }

    if (pid == 0) { --x; _exit(x); }

    if (!WIFEXITED(status) || WEXITSTATUS(status) != 8 || x != 9) return 1;

    fflush(stdout);
    pid = fork();

job / by_pid / lookup表项绑定 PID、单调 JID、状态和命令；%前缀决定按JID还是PID查找。
handler只读 foreground 并 kill 整组，保存恢复 errno；不接触复杂作业表。
reap / wait_foreground排空退出/停止/继续状态；前台尚活才原子挂起，醒后重新排空。
launch屏蔽区内 fork、双侧设组并登记；孩子重置动作与掩码；父按bg/fg分支继续。
evaluate / pselect 输入循环在主流程执行内建命令；输入按字节读，pselect 同时解决输入等待与后台回收。
cleanupEOF/quit先向全部仍登记作业的原进程组和直属PID分别发送SIGKILL，再逐PID回收；报告信号错误，向直属PID发送失败时采用非阻塞回收。

#!/usr/bin/env python3
"""Job-state reference model. The C companion supplies the actual POSIX shell."""
from dataclasses import dataclass


@dataclass
class Job:
    pid: int
    jid: int
    state: str


def transition(job, event):
    if event == "stop":
        job.state = "stopped"
    elif event == "bg":
        job.state = "background"
    elif event == "fg":
        job.state = "foreground"
    elif event in ("exit", "signal"):
        job.state = "reaped"
    else:
        raise ValueError("unknown job event")


def main():
    job = Job(100, 1, "foreground")
    for event, state in [("stop", "stopped"), ("bg", "background"),
                         ("fg", "foreground"), ("exit", "reaped")]:
        transition(job, event)
        if job.state != state:
            raise RuntimeError(f"job transition failed: {event} -> {job.state}")
    jobs = {job.jid: job}
    del jobs[job.jid]
    if jobs:
        raise RuntimeError("reaped job remains registered")
    print("shell foreground-completed jobs=0")


if __name__ == "__main__":
    main()

i 取 5、3、1，共三轮。所有进程都继续循环，每轮数量翻倍，打印 2³=8 行。不能把 n=6 直接当作 fork 次数；非负 n 的一般轮数是 ceil(n/2)。

8.20 · 把参数和环境交给 ls

题目（中文）

使用 execve 编写 myls，接受与 /bin/ls 相同的命令行参数、环境变量并生成相同输出。原题称 ls 从 COLUMNS 获取屏幕宽度，未设置时用 80；以 setenv COLUMNS 40; ./myls 和取消 COLUMNS 后再次运行比较列宽。

来源：印刷 828 页 / PDF 829 页

解答与推导

#include <stdio.h>
#include <unistd.h>
extern char **environ;
int main(int argc, char **argv) {
    (void)argc;
    argv[0] = "ls";
    execve("/bin/ls", argv, environ);
    perror("execve");
    return 127;
}

参数数组原样沿用，只把 argv[0] 换成 ls；环境传 environ，因此无需自己读取或解释 COLUMNS。成功后本程序不再存在于该进程中。可运行对应模式为 ch08_io --myls -l。题目示例的 setenv 是 csh 风格；sh/zsh 可用 COLUMNS=40 ./myls。实际列宽还受 ls 实现、是否终端和选项影响，本题的“80”是原题观察前提，不是所有系统的固定保证。

8.21 · 子进程不能等待自己的父进程

题目（中文）

列出程序所有可能输出序列。

int main() {
    printf("p"); fflush(stdout);
    if (fork() != 0) {
        printf("q"); fflush(stdout); return 0;
    } else {
        printf("r"); fflush(stdout);
        waitpid(-1, NULL, 0);
    }
    return 0;
}

来源：印刷 828—829 页 / PDF 829—830 页

解答与推导

只有 pqr 和 prq。p 在 fork 前已刷新，必然最先；q 与 r 无约束。子进程没有自己的孩子，它的 waitpid(-1,...) 返回 −1/ECHILD，不会等待父进程。因此它没有为 q→r 或 r→q 建立顺序。

8.22 · 实现 mysystem 的题定返回协议

题目（中文）

实现 int mysystem(char *command);：调用 /bin/sh -c command，等待命令结束；正常退出返回命令退出码，例如 exit(8) 返回 8；异常结束时返回 shell 的状态。

来源：印刷 829 页 / PDF 830 页

解答与推导

完整实现位于 ch08_io.c 的 mysystem：fork，子传 {"sh","-c",command,NULL} 与 environ 给 execve，失败用 _exit(127)；父对指定 PID 重试 EINTR，正常退出用 WEXITSTATUS，信号终止则返回原始 wait 状态。

int status;
while (waitpid(p, &status, 0) < 0)
    if (errno != EINTR) return -1;
return WIFEXITED(status) ? WEXITSTATUS(status) : status;

必须区分“shell 自己被信号终止”和“shell 运行的命令被信号终止后 shell 正常返回一个编码”：后者按 shell 正常退出处理，编码由 shell 决定，不能再强行把它当 WTERMSIG 解码。这个函数遵循题目规定，和标准 system 返回原始 wait 状态的接口不同；NULL、SIGINT/SIGQUIT 的特殊处理等完整 system 契约没有由题目要求，这里 NULL 明确报 EINVAL。

8.23 · 五次发送为什么只观察到两次

题目（中文）

同事用子进程发送信号通知父进程计数，每次父 handler 把全局 counter 加一。图 8.45 如下。在他的机器上子发送五次，但父最后总打印 counter=2。请解释这个 bug。

#include "csapp.h"
int counter = 0;
void handler(int sig) {
    counter++;
    sleep(1);
    return;
}
int main() {
    int i;
    Signal(SIGUSR2, handler);
    if (Fork() == 0) {
        for (i = 0; i < 5; i++) {
            Kill(getppid(), SIGUSR2);
            printf("sent SIGUSR2 to parent\n");
        }
        exit(0);
    }
    Wait(NULL);
    printf("counter=%d\n", counter);
    exit(0);
}

来源：印刷 829—830 页 / PDF 830—831 页

解答与推导

一种可行时间线：第一信号被捕获，counter=1，handler 睡 1 秒；同类信号在 handler 期间自动阻塞。第二信号置 pending=1，第三、四、五次在已有 pending 时合并。handler 返回后再处理那一个 pending，counter=2。信息已在通知层丢失，多调用 wait 或给 counter 加锁都恢复不了次数。

“总是 2”是题目那台机器的观察，换调度可得到其他次数。可靠计数应把事件写到管道或共享队列，信号只通知读取；若使用合适的实时排队信号，还需处理队列容量和发送失败。原程序 counter 也没有满足保守的信号共享类型约定；改成 sig_atomic_t 只处理访问问题，仍不能让普通信号成为计数队列。

8.24 · 观察只读代码页保护

题目（中文）

修改图 8.18 的原程序（如下），满足：① 每个子进程尝试写只读文本段后异常终止；② 父输出除 PID 外与下面相同的内容。提示：阅读 psignal(3)。

#include "csapp.h"
#define N 2
int main() {
    int status, i;
    pid_t pid;
    for (i = 0; i < N; i++)
        if ((pid = Fork()) == 0) exit(100+i);
    while ((pid = waitpid(-1, &status, 0)) > 0) {
        if (WIFEXITED(status))
            printf("child %d terminated normally with exit status=%d\n",
                   pid, WEXITSTATUS(status));
        else printf("child %d terminated abnormally\n", pid);
    }
    if (errno != ECHILD) unix_error("waitpid error");
    exit(0);
}

child 12255 terminated by signal 11: Segmentation fault
child 12254 terminated by signal 11: Segmentation fault

来源：印刷 829 页 / PDF 830 页

解答与推导

可执行实现见 ch08_io.c 的 --text-fault 分支：只在 Linux 编译这一明确有意故障的实验。父创建至多两个子进程并记录 PID；子把 main 地址按该平台指针表示转为字节地址，尝试写入。父对每个已创建子进程 waitpid，只有 WIFSIGNALED 为真才读取 WTERMSIG，并用 strsignal 生成说明；psignal 也可把前缀和说明写到 stderr。

这个操作位于 ISO C 定义行为之外，实验期待的是 Linux 可执行代码页保护结果，不是“合法 C 的一次正常存储”。在单独 Linux 环境中以未插桩构建运行 ./ch08_io --text-fault；ASan 可能接管故障并改变结束方式，不能把插桩结果当原题硬件路径。本机默认测试仅验证正常流程，不执行该特意崩溃分支。SIGSEGV 数值和说明文字也有平台、locale 边界。

8.25 · 五秒超时读取一行

题目（中文）

实现 char *tfgets(char *s, int size, FILE *stream);，参数与 fgets 相同。用户在 5 秒内没有输入一行则返回 NULL，否则返回该行的指针。

来源：印刷 830 页 / PDF 831 页

解答与推导

完整实现在 ch08_io.c 的 tfgets。用 CLOCK_MONOTONIC 建立一次 5 秒总期限；把底层描述符暂置 O_NONBLOCK，先用 fgetc 读已有 stdio 缓冲；遇到 EAGAIN 才 clearerr 并 poll 等待剩余时间。每次重试重新计算剩余时间，EINTR 不重置 5 秒。读到换行或 size−1 个字节即按 fgets 容量规则成功；EOF 时已有字符则返回部分行，无字符则 NULL。

超时返回 NULL 且 errno=ETIMEDOUT，已经消费的部分字符保留在 s 中但不算成功；最后恢复原文件状态标志。size=1 返回空串，非法大小返回 EINVAL。这种实现要求单线程且独占该 stream 及共享打开文件描述，因 O_NONBLOCK 会影响共享描述符；对仅内存流而无 fileno 的 FILE 不适用。这个边界比从 SIGALRM handler longjmp 跨出 fgets 更容易维护：后者会跳过 stdio 的内部状态清理。

运行 ch08_io --tfgets 可交互观察；管道输入 abc 立即成功，保持写端开着而不输入会约 5 秒返回状态 3，EOF 则立即按规则返回。

总期限为什么只能建一次？假设开始时为 0 秒，先等到第 4 秒收到一个字符，然后又要等换行。总期限仍是第 5 秒，剩余只能等约 1 秒；若每次收到字符就再给 5 秒，慢速输入可以让函数一直不返回，违反题目的五秒总预算。单调时钟用来算这一段持续时长，避免墙钟校时改变期限。

8.26 · 完整的作业控制 shell

题目（中文）

以图 8.23 的 read/evaluate shell 循环为起点，实现有作业控制的 shell。原起始循环如下；eval 分词后执行内建命令，或 fork/exec 可执行文件。

int main() {
    char cmdline[MAXLINE];
    while (1) {
        printf("> ");
        Fgets(cmdline, MAXLINE, stdin);
        if (feof(stdin)) exit(0);
        eval(cmdline);
    }
}

要求如下：

  1. 命令是名字及零个或多个以一个或多个空格分隔的参数；内建命令立即执行，其他名字作为可执行文件运行于新子进程，作业 PGID 等于初始子 PID。
  2. 每个作业可用 PID 或 shell 分配的正整数 JID 标识；%5 指 JID 5，5 指 PID 5。
  3. 行末 & 表示后台，否则前台。
  4. Ctrl+C/ Ctrl+Z 使内核向 shell 发送 SIGINT/SIGTSTP，再由 shell 转发到整个前台进程组。
  5. jobs 列出全部后台作业。
  6. bg job 对指定 PID 或 %JID 发 SIGCONT，并转后台。
  7. fg job 发 SIGCONT，并转前台等待。
  8. 回收所有僵尸；作业被未捕获信号终止时，打印 PID 及信号描述。

原书脚注说明上述转发是教学简化；真实 shell 用 tcsetpgrp 管理终端前台组，键盘信号由内核直接发给该组。示例会话如下，PID 仅示意：

>bogus

>foo 10

>foo 100 &
[1] 5036 foo 100 &
>foo 200 &
[2] 5037 foo 200 &
>jobs
[1] 5036 Running foo 100 &
[2] 5037 Running foo 200 &
>fg %1
Job [1] 5036 stopped by signal: Stopped
>jobs
[1] 5036 Stopped foo 100 &
[2] 5037 Running foo 200 &
>bg 5035
5035: No such process
>bg 5036
[1] 5036 foo 100 &
>/bin/kill 5036
Job 5036 terminated by signal: Terminated
>fg %2
>quit

来源：印刷 830—832 页 / PDF 831—833 页

解答与推导

完整维护实现与逐字阅读副本见 ch08_shell.c。它采用三状态作业表（前台/后台/停止）、PID/JID 查找、双侧 setpgid、非阻塞 waitpid 排空、SIGINT/SIGTSTP 向 −PGID 转发、sigsuspend 等前台条件，以及 pselect 等待命令输入。所有作业表读写都在 SIGCHLD/INT/TSTP 屏蔽期间发生；处理程序只转发信号，不分配内存或打印。

单个命令最多 127 个词，行最多 1023 字节，同时最多 32 个作业，超界明确拒绝。题目只要求空格分词，因此路径直接交 execve，不加入引号、通配符、管道或 PATH 搜索语法。--interactive 进入命令循环；默认只创建一个 /usr/bin/true 前台孩子，确认正常退出且作业表归零后结束。quit/EOF 对仍登记作业的原进程组及直属 PID 分别发送终止信号，再回收直属孩子；孩子迁到其他进程组也会按 PID 清理，信号或回收失败则以非零状态退出。

这里符合原题的信号转发模型；需要前台程序直接读取真实终端的完整 shell，还应加入 tcsetpgrp、终端属性交接等。Python 同伴只验证状态机转换与模型不变量，实际子进程、信号转发和进程组行为由 C 与 POSIX 运行测试提供证据。
