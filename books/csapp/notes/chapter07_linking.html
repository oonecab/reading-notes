7.1 · 从两份源文件到一次可执行调用Compiler Drivers

来源：印刷 707—708 页 / PDF 708—709 页

第 3 章追踪一个函数怎样变成指令，本章追踪两个分别翻译的函数怎样在地址空间里相遇。主文件知道 sum 的参数与返回类型，因而能生成调用指令；它此时不必知道 sum 的最终地址。被调文件则可以独立生成循环。链接正好填补这两个局部视角之间的空白，也让修改一个模块后只重编译它成为可能。

C：main.c 与 sum.c
/* main.c */
int sum(int *a, int n);
int array[2] = {1, 2};
int main(void) {
    int val = sum(array, 2);
    return val;
}
/* sum.c */
int sum(int *a, int n) {
    int s = 0;
    for (int i = 0; i < n; ++i) s += a[i];
    return s;
}

这是图 7.1 的算法，函数声明按 C11 原型写法整理；求和假定 n 非负、输入可读且 int 求和不溢出。原例把 3 作为 main 的返回值，所以 shell 中看到的是退出状态 3，屏幕没有打印。后面的维护源把求和等于 3 转成成功退出 0，便于自动验证。

gcc -Og -o prog main.c sum.c
gcc -v -Og -o prog main.c sum.c
gcc -c main.c
gcc -c sum.c
gcc -o prog main.o sum.o

gcc 在这里是驱动程序，会补齐启动文件、库搜索路径和链接参数。直接调用 ld 并不自动得到同一套参数。-c 停在目标文件，故“编译成功但 undefined reference”并不矛盾：语法和类型检查已结束，跨模块定义还未补齐。

阅读注解
路径

同一名字经历三种表示

C 中的 sum 是函数名；目标文件中是符号表索引；执行时是 call 的目标地址。每一步只需要下一步必须的信息。

环境

本章的具体机器是 Linux x86-64

书中 ELF、GNU ld、.so、LD_PRELOAD 属于该环境。macOS 的 Mach−O、dyld 和 .dylib 可以验证共同思想，字段及选项不能照搬。

7.2 · 先决定引用谁，再决定写入什么地址Static Linking

来源：印刷 708—709 页 / PDF 709—710 页

原文精选 · 每个引用对应一个定义

The purpose of symbol resolution is to associate each symbol reference with exactly one symbol definition.

中文释读。符号解析把每个需要外部定义的引用绑定到一个确定定义。名称相同只是匹配入口；链接器接下来还要按可见性、强弱和库搜索规则作决定。

来源：印刷 709 页 / PDF 710 页

静态链接的输入是目标文件的字节块及元数据。符号解析先回答 main.o 中的 sum 究竟采用哪一个定义；重定位再排列节与符号，改写调用和数据指针中的地址字段。前者失败表现为未定义或重复定义，后者失败可能表现为位移装不下所选字段。

阶段main.o 已有的信息sum.o 加入后得到的信息
解析引用 sum；定义 main 和 array引用绑定到 sum.o 的函数定义
布局各节局部偏移，尚无最终地址输出 .text 中 main 与 sum 的位置
修补call 后的 4 字节占位及重定位项相对下一条指令的有符号位移

链接器主要合并节、选择符号和改写指定位置，不会像 C 编译器那样重新证明所有类型正确。把一个模块的 int 和另一个模块的 double 误写成同名外部变量，正能说明“链接成功”为什么不能替代接口一致。链接时优化是额外机制，不属于本节的普通目标文件模型。

可用一次电话联系区分两个任务：先按姓名确定要联系的那个人，再取得他的号码。对应到代码，sum 的符号解析决定采用 sum.o 的定义；即便这个决定已完成，最终排布还没确定时，call 的位移仍填不出来。链接器把各模块放到具体位置后，才依据调用点与目标的位置修补字节。因此“名字已经找到”与“指令现在能跳过去”是前后两个条件。

阅读注解
区分

解析是身份，重定位是位置

两个同名强定义首先是身份冲突；目标离 call 超过范围则是表示问题。分清阶段，错误诊断才有方向。

连接

相对地址也可能需要重定位

相对编码不等于无需链接。只有调用点与目标的相对距离已由汇编器确定时，才可能在生成目标文件时填好。

7.3 · 识别要合并、要运行、要共享的文件Object Files

来源：印刷 709 页 / PDF 710 页

目标文件共同点是包含机器字节及解释这些字节的描述信息；它们的使用阶段不同。可重定位文件仍有跨模块引用要解决，可执行文件有装载所需布局，共享对象允许在装载或运行时参加链接。“object”在这里指目标模块，不是面向对象语言中的实例。

形式典型 Linux 文件由谁消费尚待处理的事情
可重定位目标main.o，ELF ET_REL静态链接器合并节、符号解析、重定位
可执行目标prog；通常 ET_EXEC，PIE 可为 ET_DYN内核装载器、动态链接器建立映射；动态依赖仍可能待绑定
共享目标libvector.so，ELF ET_DYN动态链接器选择装载基址、数据重定位与符号绑定

文件后缀只是习惯，真正类别在文件头中。共享库中的“可重定位”也不意味着它与 ET_REL 有同一种结构。现代 PIE 与共享库都可使用 ET_DYN，所以单凭该字段还不能把一个文件判定为库。ELF 是本章的具体格式；Windows 的 PE 与 macOS 的 Mach−O 实现相近目的，但文件头、节名和装载协议不同。

阅读注解
术语

源文件不是目标文件

编译后的 .o 内已经有机器指令；缺的是把各模块组合为程序所需的最终关系。

边界

可执行并不表示所有地址都已写死

动态可执行文件会保留运行时依赖和重定位。静态完整链接的示意图只是其中一种情形。

7.4 · 把文件读成若干有职责的节Relocatable Object Files

来源：印刷 710—711 页 / PDF 711—712 页

ELF 头告诉工具怎样解释整数宽度、字节序、目标机器、文件类型以及表的位置；节头表给每个节的偏移、大小和属性。读文件时不能把“文件偏移”“节内偏移”“运行时虚拟地址”混成一个数字：可重定位文件里 main 的 value 为 0，意思常是它位于自身 .text 开头，而不是最终要在虚拟地址 0 执行。

节包含什么对读者的意义
.text函数机器代码反汇编从这里开始
.rodata只读常量、格式字符串等通常映射为只读；具体归类受编译器影响
.data需在文件中保留初始值的数据例如 array={1,2} 的 8 字节
.bss需分配并清零的存储，SHT_NOBITS有内存大小，文件中不存等长零串
.symtab / .strtab符号项 / 符号名称字符串回答名字、绑定、节、大小与值
.rela.text / .rela.data 等待修补的位置与计算规则ELF64 常用显式 addend 的 RELA
.debug_* 等可选调试信息源代码行、变量位置等，不等同于链接符号

原书图 7.3 使用 .rel.text、.rel.data 作说明，而后面给出的结构带显式 addend，属于 Elf64_Rela；检查实际 x86-64 文件常会见到 .rela.text。应据 SHT_REL/SHT_RELA 及字段判断，不能只凭书中示意节名写解析器。

普通自动局部变量可能只在寄存器里，也可能放在栈上，并不按变量名在 .data 或 .bss 中各占一项。反之，函数内的 static 变量要跨调用保存值，有静态存储期，通常有相应数据节和局部链接符号；优化可能进一步删除不需要的实体。

阅读注解
空间

bss 节头有大小，节内容不占同等文件空间

一百万个初值为零的字节需要运行时存储，却不需要在文件里逐字节写入零。装载器按内存大小补齐。

读工具

调试符号和链接符号各有用途

不加 −g 仍能有 .symtab。加 −g 所增加的源级调试信息不能与函数的链接定义混为一谈。

7.5·C 作用域怎样投影到链接符号Symbols and Symbol Tables

来源：印刷 711—715 页 / PDF 712—716 页

原文精选 · 链接局部与程序局部不同

It is important to realize that local linker symbols are not the same as local program variables.

中文释读。“local”在链接器中指只在本模块内可见的符号，例如 static 函数。块内普通局部变量的名字则通常不是链接器要解析的对象。

来源：印刷 712 页 / PDF 713 页

从某个模块看，符号分三类：本模块定义、可供别处引用的 global；本模块引用、由别处定义的 external；只供本模块使用的 local。extern 是 C 声明的一种写法，ELF 的外部引用通常表现为 GLOBAL 绑定加 UNDEF 节索引，并不存在必须名为 EXTERN 的 ELF 绑定值。

源级声明/实体典型链接身份储存或引用位置
int a=3;global 定义.data
static int b;local 定义.bss
函数内 static int c=0;独特名字的 local 定义.bss，跨调用保持
extern int a; 并实际读取 aexternal 引用本模块 UNDEF；定义处才有数据节
函数内 int temp;通常无链接符号寄存器或栈；调试器可另有描述
int d; 文件作用域暂定定义原书 common 模式为 COMMON；−fno−common 为 .bss

符号表每项记录 name 的字符串表偏移、类型、绑定、节索引、value 与 size。ET_REL 中定义符号的 value 多为节内偏移；COMMON 的 value 反而表达对齐要求。UNDEF 表示当前模块未定义，ABS 表示值无需随节搬移，COMMON 是尚待分配存储的暂定定义。这些特殊索引不是文件中真的三个数据节；ABS/UNDEF 等特殊索引也不能笼统说成只可能存在于 ET_REL 文件。

原书将未初始化全局变量放 COMMON，是当时工具链的条件。GCC 10 迁移说明确认默认改成 -fno-common；此时重复暂定定义会在链接时冲突。正确共享变量的做法是一处定义、公共头文件里 extern 声明，让所有源文件读同一接口；需要重现原书历史例子时显式指定 -fcommon。

“外部引用”也不是再创建一份对象。若 a.c 中有 int total=3;，b.c 中有 extern int total; 并使用它，两边应访问同一份 total。声明向编译器交代类型，链接器再把 b.o 的引用指到 a.o 的定义。反过来，两个文件分别写 static int total;，则是各自私有的两份对象；同名不代表相同存储位置。

阅读注解
边界

static 的两种位置有共同结果

文件作用域 static 限制链接可见性；块内 static 同时具有局部作用域和静态存储期。两个函数内同名 static 变量必须是两个对象。

校注

COMMON 不是 ELF 的 STB_WEAK

原书用强弱简化讲暂定定义合并。实际 COMMON 常是 STB_GLOBAL 加 SHN_COMMON；显式 weak 属性产生的弱符号是另一套 ELF 绑定机制。

7.6 · 让名字匹配、重名规则与库顺序一致Symbol Resolution

来源：印刷 715—725 页 / PDF 716—726 页

若调用 foo 的模块只声明 foo，编译器可生成代码而把定义留给链接器；若最终所有输入里仍没有 foo，就报未定义引用。更难诊断的是多个模块都定义 x：在同一模块内，编译器可见声明冲突；分开编译后，普通链接器往往只看符号身份和大小等元数据，不执行完整 C 类型一致性检查。

7.6.1 · 重名不只是选一个地址How Linkers Resolve Duplicate Symbol Names

按书中的 common 模式：函数与已初始化的全局定义是“强”，未初始化暂定定义称“弱”；多个强定义报错，强定义覆盖同名 common，多个 common 合并为一份所需存储。最后一种书面规则说可任选弱定义，但真实 ELF common 合并还会协调大小与对齐，不能推导成任意类型写入都安全。

/* a.c */                    /* b.c */
int y = 15212;               double x;
int x = 15213;               void f(void) { x = -0.0; }

原书选定布局 x 在 0x601020、y 在 0x601024，int 为 4 字节、double 为 8 字节。若 b.c 的 x 被绑定到 a.c 的 int，写入 binary64 负零的八个小端字节 00 00 00 00 00 00 00 80，便把 x 变成 0、相邻 y 的位模式变成 0x80000000。这是特定编译/链接布局下的失误解释，C 程序的跨模块不兼容声明本身违反语言要求，不能当成可移植技巧或保证输出。

修复应是匹配接口或把不相关对象设为 static。不要靠变量顺序、优化级别或链接器碰巧合并来维持正确性。原书建议的 −fno−common 直接针对此类暂定定义冲突；-Werror 也不能代替链接器自身诊断选项。

7.6.2 · 静态库把选择单位留在成员目标文件Linking with Static Libraries

把所有库函数放一个 libc.o 会让使用者带入整块模块；让调用者手写每个对象又难维护。归档库把多个 .o 装进一个 .a，链接器按未解决符号挑选成员。传统选择单位是一个目标成员：需要 addvec.o 的某个定义就可能带入该成员中的其他函数和数据；更细粒度删除另有节回收机制。

gcc -c addvec.c multvec.c
ar rcs libvector.a addvec.o multvec.o
gcc -o prog main2.o ./libvector.a

main2.o 引用 addvec，就抽取 addvec.o；没有引用 multvec.o 的定义就不抽取它。只有 -lvector 时，工具链还可能优先选同名共享库；写出 ./libvector.a 才明确选择这个归档。程序使用一个静态库也不等于整个可执行文件静态链接，其他运行库可以继续动态依赖。

7.6.3 · 沿命令行维护已选、待解与已定义集合How Linkers Use Static Libraries to Resolve References

原文精选 · 输入顺序影响归档提取

Initially, E, U, and D are empty.

中文释读。E 是已选目标模块，U 是尚无定义的引用，D 是已见定义。三个集合从空集开始，处理每个输入时更新，因此后来出现的引用不会自动让已经扫过的库重新开始。

来源：印刷 724 页 / PDF 725 页

普通 .o 无条件加入 E；将其定义加入 D，再把新增引用中不在 D 的加入 U。遇到库时，只选“定义能满足当前 U”的成员，并在这个库内部反复检查，直到没有新成员可选。随后继续下一个命令行参数。书中的传统左到右算法不会自动回头访问早先的另一座库；特定链接器扩展可能放宽这个限制，不能把宿主差异当成书中模型失效。

读入输入新抽取成员DU
p.op，引用 x1{p}{x1}
libx.ax1，引用 y；x2 尚未需要{p,x1}{y}
liby.ay，引用 x2{p,x1,y}{x2}
再次 libx.ax2，引用 p 已满足{p,x1,y,x2}∅

因此这组具体成员需要 p.o libx.a liby.a libx.a。把两个库合并成一个归档则可在库内求不动点；GNU 链接器也有 group 选项反复扫描库组。重复普通 p.o 会再次加入它并可能造成多定义，不能把库循环依赖机械地翻译为重复每个文件。后面的模型给出同一轨迹及错误顺序。

“扫描到库时才按需抽取”意味着：若命令把 libsum.a 放在 main.o 前，在本节传统模型里，此刻未解集合 U 还没有 sum，库成员便不会被抽取；读到 main.o 后才产生 sum 的需求，却已经走过那座库。库文件中确实存在 sum，仍可能得到未定义引用。把使用者放前、提供定义的库放后，就是让需求先进入 U，再让库满足它。

阅读注解
不变量

U 总是不含 D 中的符号

每次加入成员都先扩大 D，再从全部引用中删去 D。一个新成员可能解决旧引用，也可能引入新引用。

粒度

库依赖箭头没有指定成员结构

习题的最短序列按教材给定抽取链解释。真正的最短命令仍取决于哪些函数同属一个 .o，复杂交叉引用可能需要更多扫描。

7.7 · 逐字节算出链接器要修补的值Relocation

来源：印刷 725—731 页 / PDF 726—732 页

解析结束后，每个引用已有定义，链接器先合并同类节并给它们和符号分配地址，再修改代码和数据中的引用。原书假设布局已经选定；真正链接器还要满足对齐、权限和格式约束。下面保持原书那组确定地址，使每个十六进制数都能追到指令中的位置。

7.7.1 · 一条重定位项说明位置、对象、算法和加数Relocation Entries

字段原例调用 sum含义
offset0xf待写的 4 字节字段在输入 .text 内的偏移
symbolsum已经完成解析的目标定义
typeR_X86_64_PC32写入有符号 32 位 PC 相对位移

令 S 为目标符号地址、A 为 addend、P 为被修补字段自身的地址。PC32 计算 S+A−P；R_X86_64_32 计算 S+A，并要求结果可由 32 位零扩展表示。PC32 则要求结果能放入有符号 32 位。原书伪代码把结果强制转为 unsigned，省略了真实链接器的范围检查；教学程序在写字节前显式检查，越界保持输出不变。

7.7.2 · 把字段地址与下一条指令分开Relocating Symbol References

PC32：写入值=S+A−P；P=ADDR(.text)+offset

本例 .text 基址为 0x4004d0，sum 为 0x4004e8。call 起始偏移为 0xe，但操作码 e8 占一字节，所以待修改字段的偏移为 0xf，P=0x4004df。字段占 4 字节，执行时下一条指令地址为 P+4=0x4004e3。于是 S−(P+4)=0x4004e8−0x4004e3=5，等价于 S+(−4)−P。

4004de: e8 05 00 00 00    callq 4004e8 <sum>
4004d9: bf 18 10 60 00    mov   $0x601018,%edi

另一条 mov 的立即数字段位于 .text 偏移 0xa，它引用 array，A=0，因而写入 S=0x601018，小端排列为 18 10 60 00。如果代码和目标整体平移相同距离，S−P 不变；绝对地址则要变化。这正是后面 PIC 的基础。

负位移仍按补码字节写入：目标 0x4004d0、P=0x4004df、A=−4 时差为 −19，4 字节为 ed ff ff ff。CPU 把该字段符号扩展后相加，不能把它理解为向前跳约 4 GiB。现代工具的外部 call 常生成 R_X86_64_PLT32；它以 PLT 入口等链接选择为对象，不能仅把类型名称替换后断言与书中所有情形相同。

阅读注解
易错

−4 来自字段长度，不是 opcode 长度

r.offset 指向立即数字段，opcode 在它前一字节。减去四字节才把 P 移到 CPU 使用的下一条指令。

边界

截断前必须知道是否可表示

PC32 的范围是 −231 到 231−1；R_X86_64_32 是 0 到 232−1。直接取低 32 位会把不可达地址伪装为正常编码。

7.9 · 从文件映射到 main 前的启动过程Loading Executable Object Files

来源：印刷 733—734 页 / PDF 734—735 页

7.12 · 用不变的相对距离访问会变的地址Position-Independent Code (PIC)

来源：印刷 740—743 页 / PDF 741—744 页

原文精选 · 代码可共享，可写状态仍分开

Of course, each process will still get its own copy of the read/write data segment.

中文释读。PIC 的目标是使代码不因各进程装载地址而被改写。需要填入真实地址的信息可放到各进程的数据区；可写段仍归各进程所有。

来源：印刷 740 页 / PDF 741 页

给每个库永久预留一个全局固定地址既浪费空间又难协调。PIC 利用模块内部偏移不随整体装载基址改变：若一条指令与它的 GOT 项同时加上基址 B，两者之差不变。代码因此能通过 RIP 相对寻址找到自己的 GOT，再从 GOT 取出可能位于任意库中的真实符号地址。

PIC 数据引用：先到 GOT，再到对象

(B+GOT_offset)−(B+next_instruction_offset)=GOT_offset−next_instruction_offset
mov 0x2008b9(%rip), %rax  # %rax = GOT 中保存的 &addcnt
addl $1, (%rax)            # 对 addcnt 所在地址加 1

第一条读的是 GOT 里的指针，不是 addcnt 的数值；第二条才修改该指针指向的整数。位移 0x2008b9 对应第一条之后的 RIP 到 GOT 项的距离。动态链接器修改 GOT 中的地址即可保留代码字节不变。对明确不能被插入替换的本模块符号，编译器/链接器还可能消除中转；一般可抢占的全局符号必须保持正确的动态符号绑定语义。

PIC 函数调用：第一次经过解析器，后来直接跳转

第一次 call 先进入 PLT[2]，其间接跳转回到自身后半部，借 PLT[0] 进入动态链接器。解析器知道“哪个模块、哪一条重定位”，找到 addvec 后更新 GOT[4]。第二次仍到同一 PLT[2]，但间接跳转已通往真实函数。首次多走的路径换来启动时少解析那些从未调用的函数。

PIC 并不要求一定惰性绑定；立即绑定同样可以把所有地址先写入 GOT，也有不经过传统 PLT 的调用生成方式。PIC 所谓“不需要重定位”应理解为无需因装载基址再改写其可共享代码，不代表共享对象完全没有任何动态重定位。本文不会把书中固定 16 字节 PLT、8 字节 GOT 及具体槽位编号推广为所有 ISA/工具链的规则。

用具体数值区分两次读取：假设某条指令之后的 RIP 为 0x1000，它的 GOT 项在 0x1800，项内保存 0x7000，地址 0x7000 的整数值为 3。第一条 RIP 相对 load 用位移 0x800 找到表项，得到指针 0x7000；第二条才按这个指针把对象从 3 改成 4。若模块整体搬高 0x10000，指令与 GOT 项之间仍差 0x800；表项内的最终对象地址则由动态链接确定。表项地址、表项存的指针、指针所指整数必须分别跟踪。

阅读注解
推导

同加基址为什么会抵消

RIP 相对地址的两端都在同一装载模块且布局固定时，基址 B 在减法里消去；指向另一库的最终地址没有这种保证。

边界

延迟绑定是一种策略，PIC 是代码性质

完全立即绑定的库仍可使用 PIC；能用 RIP 相对寻址的指令也不保证所有外部引用无需处理。

7.13 · 在三个时机把调用导向包装函数Library Interpositioning

来源：印刷 743—748 页 / PDF 744—749 页

库打桩在目标函数前后加一层相同原型的包装，可记录参数、统计调用或替换实现。关键不是包装内部多写几行，而是把调用者原本的引用改到包装，同时保留访问真实函数的路径。教材用 malloc/free 演示；这类分配器包装还必须面对日志函数自身可能分配内存的递归问题。

7.13.1 · 预处理阶段替换可见调用Compile-Time Interpositioning

/* 仅调用者包含这份头文件；包装实现应包含标准头文件。 */
#define malloc(size) mymalloc(size)
#define free(ptr) myfree(ptr)
void *mymalloc(size_t size);
void myfree(void *ptr);

调用者预处理后的名称已经是 mymalloc/myfree，所以需要拿到源文件并重编译。包装模块不能再次套用同一宏，否则它想调用真实 malloc 时又调用自己。这个方法只覆盖实际经过该头文件的源代码，已编译的库内部调用不会因此重写。头文件还必须提供 size_t 的声明，例如先包含 stddef.h。

7.13.2 · 链接时把未解决引用改名Link-Time Interpositioning

gcc -Wl,--wrap,malloc -Wl,--wrap,free -o app app.o wrappers.o

GNU ld 的 --wrap,malloc 让指向 malloc 的未解决引用转向 __wrap_malloc，包装中对 __real_malloc 的未解决引用则转回真实 malloc。此时需要目标文件，未必需要原源代码；已经在同一对象内部绑定或被编译器优化掉的调用可能不进入这条路径。-Wl, 是驱动将参数传给链接器的语法，macOS ld 不应假定支持同一选项。

7.13.3 · 装载时优先查找插入库Run-Time Interpositioning

gcc -shared -fPIC -o wrappers.so wrappers.c -ldl
LD_PRELOAD=./wrappers.so ./app

在支持该机制的 Linux 动态链接环境，LD_PRELOAD 把指定库置于优先搜索位置，包装再用 dlsym(RTLD_NEXT,"malloc") 查找搜索顺序中后续实现。它可以处理无需重编译的动态程序，但不是原书口语化“任何可执行程序”的无条件保证：静态程序、隐藏或内部绑定符号、编译器内联，以及安全执行模式的环境限制，都可能使它不生效。

教材的 printf 日志帮助解释控制流，完整分配器拦截不能直接照抄成生产设施。printf 和 dlsym 的内部都可能触发分配；首次解析、递归、线程间初始化、错误报告和信号环境都要单独设计。free 的日志若放在真正释放后，还涉及释放后指针值的语言边界。这里保留机制与原书来源，并用不拦截分配器的独立插件实验验证动态加载接口。

阅读注解
比较

源文件、目标文件、可执行文件对应三种介入点

编译时需源代码；链接时需可链接对象；装载时需动态符号路径。越晚介入，可改变的范围越受既有构建选择限制。

记录 malloc 的日志可能再次调用 malloc；必须在设计时考虑递归，不能把输出偶尔正确当成拦截器已完备。

/* Inputs are 32-bit addresses; int64_t safely holds S + A - P. */
static bool relocate(uint32_t symbol, int32_t addend, uint32_t place,
                     bool pc_relative, unsigned char out[4]) {
    int64_t value = (int64_t)symbol + addend;
    if (pc_relative) value -= place;
    if ((pc_relative && (value < INT32_MIN || value > INT32_MAX)) ||
        (!pc_relative && (value < 0 || value > UINT32_MAX))) return false;
    uint32_t bits = (uint32_t)value;
    for (unsigned i = 0; i < 4; ++i)
        out[i] = (unsigned char)((bits >> (8U * i)) & UINT32_C(255));
    return true;
}

    if not (0 <= symbol <= 0xffffffff and 0 <= place <= 0xffffffff
            and -(1 << 31) <= addend < (1 << 31)):

库扫描的 E、U、D 轨迹

C 以四位掩码表示 p、x1、x2、y，Python 则用有名字的集合，便于交叉核对。include 将模块加入 E、定义并入 D，并令 U=(U∪新引用)−D。archive 只选能满足 U 的成员，并循环到没有新成员。libx 的成员故意把 x2 排在 x1 前，合并库再把需要的后续成员放在前面，以检验库内部必须反复扫描。

六个案例包括正确回扫、漏回扫、库过早出现、合并为单库、空输入与完全未使用库。输出 unresolved 的 2 表示 x1、4 表示 x2。此模型仅有唯一强定义，不模拟弱绑定、重复定义、LTO、真实 ELF 解析或特定链接器的自动回扫扩展。

/* C11 model of textbook left-to-right archive extraction. */
#include <stdbool.h>
#include <stddef.h>
#include <stdio.h>

/* Bits 0..3 denote p, x1, x2, y. All definitions here are unique. */
struct module { const char *name; unsigned defines, uses; };
static const struct module modules[] = {
    {"p", 1U, 2U}, {"x1", 2U, 8U}, {"x2", 4U, 1U}, {"y", 8U, 4U}
};
struct state { unsigned included, defined, unresolved; };

static void include(struct state *s, size_t i) {
    s->included |= 1U << i;
    s->defined |= modules[i].defines;
    s->unresolved = (s->unresolved | modules[i].uses) & ~s->defined;
    printf(" %s", modules[i].name);
}

static void archive(struct state *s, const size_t *members, size_t count) {
    bool changed;
    do {
        changed = false;
        for (size_t k = 0; k < count; ++k) {
            size_t i = members[k];
            if (!(s->included & (1U << i)) &&
                (modules[i].defines & s->unresolved)) {
                include(s, i);
                changed = true;
            }
        }
    } while (changed);
}

static unsigned run(const char *name, const char *order) {
    struct state s = {0, 0, 0};
    const size_t x[] = {2, 1}; /* x2 before x1 forces within-archive iteration */
    const size_t y[] = {3};
    const size_t all[] = {2, 3, 1};
    printf("%s:", name);
    for (; *order; ++order) {
        if (*order == 'p') include(&s, 0);
        else if (*order == 'x') archive(&s, x, 2);
        else if (*order == 'y') archive(&s, y, 1);
        else if (*order == 'a') archive(&s, all, 3);
    }
    printf(" | unresolved=%u\n", s.unresolved);
    return s.unresolved;
}

int main(void) {
    if (run("good", "pxyx") != 0) return 1;
    if (run("one-pass", "pxy") != 4) return 1;
    if (run("early-archive", "xpy") != 2) return 1;
    if (run("combined", "pa") != 0) return 1;
    if (run("empty-input", "") != 0) return 1;
    if (run("unused-libraries", "xy") != 0) return 1;
    return 0;
}

"""Textbook archive scan, using named sets instead of C bit masks."""
MODULES = {
    "p": ({"p"}, {"x1"}),
    "x1": ({"x1"}, {"y"}),
    "x2": ({"x2"}, {"p"}),
    "y": ({"y"}, {"x2"}),
}
ARCHIVES = {"x": ["x2", "x1"], "y": ["y"], "a": ["x2", "y", "x1"]}
BITS = {"p": 1, "x1": 2, "x2": 4, "y": 8}


def run(name, order):
    included, defined, unresolved = [], set(), set()

    def include(member):
        nonlocal unresolved
        defs, uses = MODULES[member]
        included.append(member)
        defined.update(defs)
        unresolved = (unresolved | uses) - defined

    for item in order:
        if item == "p":
            include("p")
            continue
        while True:
            before = len(included)
            for member in ARCHIVES[item]:
                if member not in included and MODULES[member][0] & unresolved:
                    include(member)
            if len(included) == before:
                break
    mask = sum(BITS[symbol] for symbol in unresolved)
    print(name + ":" + "".join(" " + m for m in included)
          + f" | unresolved={mask}")
    return mask


def main():
    for name, order, expected in [
        ("good", "pxyx", 0), ("one-pass", "pxy", 4),
        ("early-archive", "xpy", 2), ("combined", "pa", 0),
        ("empty-input", "", 0), ("unused-libraries", "xy", 0),
    ]:
        if run(name, order) != expected:
            raise RuntimeError(f"incorrect archive extraction: {name}")


if __name__ == "__main__":

原位移为 0x1200−4−0x1001=0x1fb，下一条地址 P+4=0x1005，再加位移到 0x1200。两端同加基址后差不变，仍为 0x1fb；只给 S 加 16 后变为 0x20b。PIC 能利用的是相对距离不变，不是所有对象都不会移动。

A. 若 .text 迁移到 0x4004e0，swap 迁移到 0x4004f8，callq 中重定位引用值是多少？

B. 若 .text 迁移到 0x4004d0，swap 迁移到 0x400500，结果又是多少？

解答

两问都用 P=段基址+0xa 和 S−4−P：

情形P下一条 P+4SS−(P+4)写入小端字节
A0x4004ea0x4004ee0x4004f80xa0a000000
B0x4004da0x4004de0x4005000x2222 00 00 00

A 与练习 7.5 的调用点和目标同时向后平移 0x10，因此位移仍为 0xa。B 的调用点与 7.5 相同，目标多后移 0x18，所以位移从 0xa 增为 0x22。两行均在重定位 C/Python 模型中用独立常量核对。

7.13 · 用本机工具回答环境相关问题

原题（中文翻译）

来源：印刷 753 页 / PDF 754 页

完成下列操作以熟悉目标文件工具。

A. 你系统上的 libc.a 和 libm.a 各包含多少个目标文件？

B. gcc -Og 和 gcc -Og -g 是否产生不同的可执行代码？

C. 你系统上的 gcc 驱动程序使用哪些共享库？

解答

这题没有跨机器统一的数字，先确认实际编译器身份，再选择它使用的库，避免把任意磁盘上的同名文件当成系统版本。Linux GNU 工具链的可复现步骤如下：

Shell：查询库文件与符号
gcc --version
gcc -print-file-name=libc.a
gcc -print-file-name=libm.a
# 对上一条返回且实际存在的归档路径执行：
ar t /实际路径/libc.a | wc -l
ar t /实际路径/libm.a | wc -l
# 若路径指向链接脚本或薄归档，先识别格式并按成员语义统计。

gcc -Og -c ch07_link_sum.c -o plain.o
gcc -Og -g -c ch07_link_sum.c -o debug.o
objcopy --only-section=.text -O binary plain.o plain.text
objcopy --only-section=.text -O binary debug.o debug.text
cmp plain.text debug.text
# 对可信的实际 gcc 驱动（如需先解析符号链接）查看直接依赖：
ldd /实际路径/gcc

A 的本机结果：此次环境是 macOS arm64、Apple Clang 17；系统 gcc 命令也报告 Apple Clang。-print-file-name=libc.a 与 libm.a 返回未解析的同名文本，路径检查确认未取得这两个可统计归档，因此答案是“此工具链未提供可由该查询定位的归档，计数不适用”，不能填 0，也不能引用书中历史大小猜个数。

B 的本机结果：对随页维护源 ch07_link_sum.c 分别 −Og 与 −Og−g 编译，otool 提取的 __TEXT,__text 指令字节完全相同；−g 增加调试元数据。应比较代码节而非整个目标文件，也应保留“此编译器和此程序”的范围；调试选项不在 C 语言层面承诺所有构建逐字节一致，最终链接地址还可能受其他布局影响。

C 的本机结果：otool -L /usr/bin/gcc 列出 /usr/lib/libxcselect.dylib 与 /usr/lib/libSystem.B.dylib。该路径是 Apple 工具选择入口；它选择的真正 Clang 驱动是另一可执行文件，不能把入口的两项直接依赖说成整个工具链、cc1、汇编器与链接器的所有依赖。

ch07_probe.py把分离编译、归档、缺符号失败、代码字节对比与动态加载实验的命令和结果保存在指定忽略目录。它显式记录平台，避免用 Mach−O 实验冒充 Linux ELF 执行。
