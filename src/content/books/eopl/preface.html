Abelson 导读：解释器也是一个程序

“The interpreter for a computer language is just another program.”

译义：一门计算机语言的解释器，本身也只是一个程序。

Foreword，p.ix / PDF 10，开篇独立句。

这句话首先改变了规则的地位。站在语言使用者一侧，我们接受别人规定的语法和行为；站到解释器内部，规则变成了可以阅读、修改和检验的程序。变量查找是一段代码，过程调用是一段代码，异常传播也是一段代码。设计语言的能力由此变得具体：先决定希望程序怎样运作，再把这个决定落实为解释器的行为。

Abelson 用自己早年编写大型系统的经历说明这种转变。若只把现成语言当成固定功能菜单，程序容易成为大量特殊情况的拼接。若能识别系统里的小语言，就可以为数据组合、任务编排或规则表达设计一致的语法与含义，使功能通过共同规则组合起来。这里的小语言不一定是完整的通用语言；一种查询表达式、配置规则或操作序列，都可能需要名字、组合方式和执行含义。

他的论证分三步推进。首先，大型系统需要把部件组合起来，而组合规则往往具有语言结构。其次，即使项目没有叫“解释器”的文件，它也可能不断接收并执行某种指令或描述，已经承担了语言处理的工作。最后，作用域、过程、状态等语言机制本身也是组织复杂软件的工具；理解它们，才能判断哪种组合方式适合当前问题。

因此，导读所说的掌握解释器，不只是看懂几行求值代码。更重要的是提出可检验的设计问题：某个绑定应该在哪个范围可见？一个参数应该立刻计算，还是等用到时再计算？两个组件共享的到底是值还是可变位置？这些问题会在后续章节中变成一对一对可以比较的语言设计。

第三版附加的导读后记把这一视角放进当时的浏览器脚本、游戏、数据处理和传感器等应用中。那些具体应用属于 2007 年的写作背景；今天阅读时应抓住其共同点：新框架仍需要规定组合、控制和数据的意义。导读署名为 Hal Abelson，Cambridge, Massachusetts，September 2007。

阅读注解
理解“可修改”

改变规则，要能观察到差别

给解释器换一种内部数据结构，可能保持程序行为不变；把词法作用域改成动态作用域，则会改变某些程序的结果。两类修改都重要，但需要不同的验证问题。

作者的目标：对“它做了什么”给出可执行回答

“What does it do?”

译义：它会做什么？

Preface · Goal，p.xv / PDF 16，作者提出的核心问题。

语法说明哪些文本是合法程序；语义说明这些程序会怎样运行、产生什么值或效果。作者希望读者获得一种能够实际使用的理解：遇到陌生语言特性时，能分析它的行为，而不只记住术语。解释器之所以适合承担这一任务，是因为它必须把每一种语法构造的处理方式写清楚，而且这些规定可以真的执行。

例如，“局部变量有作用域”仍不足以解释过程体里的自由变量。变量该在过程定义处查找，还是在调用处查找？过程创建后，外围绑定的生命周期又怎样影响它？若只用口头描述，很容易把两个问题混在一起；解释器则必须明确保存什么、调用时又从哪里查询。

本书把 Scheme 用作实现语言，把 LET、PROC 等用作被定义语言。前端把源文本变成 AST，解释器再按 AST 的构造求值。作者还讨论把一种程序结构变成另一种结构的翻译器，以及在运行以前检查类型的分析器；它们分别回答“怎样换一种表达仍保留行为”和“哪些错误可以提前排除”。

有了可执行实现，也仍然需要推理。跑通十个程序只能说明这十个结果符合预期；要理解一条规则为什么适用于所有合法输入，仍要分析语法分支、递归结构和所保持的不变量。作者强调代数推演和小步骤变换，正是为了让运行观察和一般解释互相支持。

先算一个例子：闭包记住哪一个 x

伴读原创例子 · 同一个调用，两个作用域规则

机制依据：§3.3，pp.74–80 / PDF 97–103；动态绑定变体见习题 3.28，p.82 / PDF 105。本例不是原书编号例题。

下面使用 PROC 风格的写法。-(a,b) 表示 a 减 b；proc (y) body 创建一个以 y 为形参的过程；(f 25) 调用 f。

let x = 10
in let f = proc (y) -(y,x)
   in let x = 20
      in (f 25)

先不要运行。我们只采用四条规则：let 在当前环境计算右侧，再扩展环境求主体；变量查询沿环境链寻找最近绑定；创建过程时保存形参、过程体和当时环境；调用时先在调用者环境计算过程与实参，再在保存环境上增加形参绑定来执行过程体。

第一步：把最外层的 x 绑定为 10，得到环境 E1。可以把它画成一个节点 x↦10，后面连接空环境。此时还没有 f，也没有内层的 x。

第二步：在 E1 中求 proc (y) -(y,x)。这里暂不执行减法，而是创建闭包 〈y,−(y,x),E1〉。把这个闭包绑定给 f 后得到 E2。闭包保存的是创建时的 E1，它知道自由变量 x 应沿哪条环境链查询。

第三步：内层 let x = 20 在 E2 前面增加一个新节点，得到 E3。E3 中最近的 x 是 20，但旧的 E1 仍然存在。这一步是遮蔽：增加一个更近的同名绑定；这里没有赋值操作，也没有把 E1 中的 10 改成 20。

第四步：在 E3 中求 f，得到第二步创建的闭包；在 E3 中求实参 25，得到整数 25。按词法规则，给闭包保存的 E1 加上 y↦25，得到执行过程体的 E4。于是 y 查到 25，x 沿 E4 的父链查到 10。

25−10=15

如果有意把调用规则改成“扩展调用者环境 E3”，新环境的父链上最近的 x 就是 20，结果变为 25−20=5。这是一个动态作用域变体。两个结果的差异来自查找环境的选择，而不是减法算法或源程序文本发生了变化。

规则过程体所在环境读到的 y、x结果
词法作用域形参绑定 → 创建环境 E125、1015
本例动态变体形参绑定 → 调用环境 E325、205

这就是序言所说的“用解释器表达语言设计”：规则落在一个可以指认的位置上，而且有一个小程序能区分两种设计。以后读到存储、续文和类型环境，也应该寻找同样具体的表示与选择。

让这个规则真的运行

配套程序用 Python 的不可变链保存环境。Env 的每个节点保存一个名字、一个绑定值和父环境；Closure 保存形参、体和创建环境。在 let 分支中，右侧先用旧环境求值，新绑定只给主体使用；在 call 分支中，过程和实参都先在调用环境求值。

最关键的一行是 parent = procedure.saved_env if scope == "lexical" else env。默认词法规则选闭包的环境，动态比较选调用者环境。接下来的 Env(procedure.param, argument, parent) 在选好的父环境前面增加形参绑定；整个例子中的 15 与 5 就来自这里。

代码直接接收 AST，省去解析器，让注意力集中在规则上。它只有整数、变量、减法、局部绑定、过程和调用六种构造；它没有实现原书完整 PROC 或 Scheme。验证器先检查整棵有限 AST，未知变量、对非整数求差、调用非过程会报告 LanguageError。Python 的 bool 被明确排除在整数常量之外。

完整 Python 3 实现与演示输入 
#!/usr/bin/env python3
"""序言原创例子：六种 AST 构造，显式环境与闭包；Python 3.10+。"""
from __future__ import annotations

from dataclasses import dataclass
from typing import Any


class LanguageError(ValueError):
    """模型程序的非法语法或运行错误。"""


@dataclass(frozen=True)
class Env:
    name: str
    value: Any
    parent: Env | None

    def lookup(self, name: str) -> Any:
        frame: Env | None = self
        while frame is not None:
            if frame.name == name:
                return frame.value
            frame = frame.parent
        raise LanguageError(f"unbound variable: {name}")


@dataclass(frozen=True)
class Closure:
    param: str
    body: tuple
    saved_env: Env | None


def validate(expr: tuple) -> None:
    """只接受 const/var/diff/let/proc/call，先验证整个有限 AST。"""
    if not isinstance(expr, tuple) or not expr:
        raise LanguageError("expression must be a nonempty tuple")
    tag, *parts = expr
    arities = {"const": 1, "var": 1, "diff": 2,
               "let": 3, "proc": 2, "call": 2}
    if not isinstance(tag, str) or tag not in arities:
        raise LanguageError("unknown expression tag")
    if len(parts) != arities[tag]:
        raise LanguageError(f"wrong AST arity: {tag}")
    if tag == "const":
        if type(parts[0]) is not int:
            raise LanguageError("constant must be an integer")
    elif tag in ("var", "let", "proc"):
        if not isinstance(parts[0], str) or not parts[0].isidentifier():
            raise LanguageError("invalid variable name")
        for child in parts[1:]:
            validate(child)
    else:
        for child in parts:
            validate(child)


def evaluate(expr: tuple, *, scope: str = "lexical") -> int | Closure:
    """按值、从左到右求值；dynamic 是用于比较的语言变体。"""
    if scope not in ("lexical", "dynamic"):
        raise LanguageError("scope must be lexical or dynamic")
    validate(expr)

    def value_of(node: tuple, env: Env | None) -> int | Closure:
        tag, *parts = node
        if tag == "const":
            return parts[0]
        if tag == "var":
            if env is None:
                raise LanguageError(f"unbound variable: {parts[0]}")
            return env.lookup(parts[0])
        if tag == "diff":
            left = value_of(parts[0], env)
            right = value_of(parts[1], env)
            if type(left) is not int or type(right) is not int:
                raise LanguageError("difference expects integers")
            return left - right
        if tag == "let":
            name, rhs, body = parts
            value = value_of(rhs, env)
            return value_of(body, Env(name, value, env))
        if tag == "proc":
            param, body = parts
            return Closure(param, body, env)
        # validate 已保证余下的构造只可能是 call。
        procedure = value_of(parts[0], env)
        argument = value_of(parts[1], env)
        if not isinstance(procedure, Closure):
            raise LanguageError("call expects a procedure")
        parent = procedure.saved_env if scope == "lexical" else env
        return value_of(procedure.body, Env(procedure.param, argument, parent))

    return value_of(expr, None)


DEMO = (
    "let", "x", ("const", 10),
    ("let", "f", ("proc", "y", ("diff", ("var", "y"), ("var", "x"))),
     ("let", "x", ("const", 20), ("call", ("var", "f"), ("const", 25))))
)


if __name__ == "__main__":
    for mode in ("lexical", "dynamic"):
        result = evaluate(DEMO, scope=mode)
        print(f"{mode}: {result}")
阅读注解
为第 4 章留一个问题

保存环境，不总是冻结值

本例没有可变存储，因此保存的绑定保持为 10。到了 IMPLICIT-REFS，环境保存的是位置；闭包若保存同一位置，以后再读取就可能看到赋值后的值。词法作用域决定绑定到哪里，不保证那里存放的值永远不变。

六项方法怎样共同支持理解

Preface · Goal 后的六项方法，p.xvi / PDF 17。下表为逐项释义与伴读说明。

作者的六项方法可以沿一次实验连起来：先把问题缩小到一种语言，再给出可执行规则；用接口隔开表示，才能尝试不同实现；通过逐步变换连接高层解释和低层机制；最后以推演和习题检验每个选择。

原序言的方法为什么需要它本例中的落点
1. 用小语言介绍新概念，常逐步累积把注意力集中在新增机制与已有机制的相互作用上。只用 let、proc、调用和差，已经能分辨作用域。
2. 以解释器、类型检查器表达设计自然语言中的含糊选择必须落实为完整处理规则，且能够执行。调用时选择 saved_env，结果由此确定。
3. 用接口与规格建立数据抽象改变表示时，不必让所有使用者跟着改变。环境查询有明确行为，后续可换表示。
4. 在高层与低层多个抽象层次书写既能看清意义，也能理解实现需要保存哪些状态。“保存创建环境”对应闭包字段和环境链。
5. 用代数式推演预测行为与性质结果有可跟随的依据，能够辨认程序运行中的关键步骤。先确定 x 与 y，再推出 25 − 10。
6. 通过习题研究替代设计比较能揭示原选择的作用，也能暴露设计之间的相互影响。动态作用域变体得到 5，区分用例因此成立。

其中数据抽象会反复出现。第 2 章比较环境的不同表示，第 3 章表示过程，第 5 章表示续文，第 8 章用类型系统约束模块客户。每一次都要先问：外部可观察的操作是什么？哪些内部细节可以换掉？这种连续性，是把整本书读成一条主线的关键。

也不必把“少用数学符号”理解成不需要严谨性。程序的输入输出约定、递归终止所依据的更小结构、分支是否穷尽合法情况，都承担着数学约束的作用。代码短只是起点，能说明它为什么这样写才是阅读目标。

第三版做了什么，全书怎样展开

Preface，p.xvii–xviii / PDF 18–19。

本次资料是第三版。作者特别说明：为非平凡定义加入非正式的输入输出契约；模块章为新内容；第 6 章改用一阶、组合式的 CPS 变换方法。这里“一阶”说的是变换算法所采用的方法，不意味着被研究的语言取消了高阶过程。

为了突出机制，第三版第 3、4、5、7、8 章的主体语言把过程简化为单参数，多参数扩展放入习题。第 6 章和第 9 章则使用多参数过程。阅读代码或找习题答案时需要先核对版次及语言，不能把不同章节的语法假设直接拼在一起。

作者的组织安排是先准备工具，再解释行为，最后组合机制。前两章讨论归纳数据和抽象表示；第 3 章建立带词法作用域、一等过程和递归的解释器，并引入词法地址；第 4 章加入存储；第 5、6 章研究控制与 CPS；第 7 章加入类型检查和推断；第 8 章建立模块边界；第 9 章把状态、分派与类型组合成对象系统。

两条容易读混的线需要先分开。第 5 章把“解释器自身”改成续文传递形式，第 6 章则写一个转换器，把一般源程序转成 CPS。第 7 章研究静态分析时，回到第 3 章语言建立类型规则，并不要求先把所有控制扩展合并。完整依赖关系与每章落点见全书依赖图。

附录 A 说明思想来源，适合带着概念回查文献；附录 B 介绍 SLLGEN，帮助把输入字符串变成 AST。两者分别支持追根溯源和动手实现。

怎样使用这本书

Preface · Usage，p.xix / PDF 20。

作者面向有数据结构基础、具有命令式语言经验，并接触过 Scheme、ML、Python 或 Haskell 这类语言的读者。原因很实际：你既要理解变量更新和控制执行，也要把过程当作可传递、可返回的数据。若这两方面有一方面不熟，先用很小的程序补齐，再进入解释器。

习题是正文的一部分。作者建议每题都至少读过并思考；一星到三星表示从理解相关内容即可解决，到需要较多思考和编程的不同难度，不是严格的耗时配额。有些习题改变语言设计，有些改变实现表示，还有些把同一机制带到后续语言中。只读主文会错过这些比较。

一个可持续的读法是：先给程序的输入、输出和语法分支做标记，再手算一个正常例子及一个能区分错误实现的例子，随后运行，最后改变一处规则。例如本页用同名遮蔽区分创建环境和调用环境；若程序没有这处遮蔽，两种实现可能输出相同值，就不足以检验闭包规则。

作者说明，支持一等过程和赋值的语言都可用于完成习题。原书配套实现使用当时的 PLT Scheme，代码大体兼容 R5RS。这是原书的环境说明；本批实际执行的是前述 Python 教学模型，原书 Scheme 全套解释器的环境准备和运行留到相应章节记录。

现在可以带着三个具体问题进入第 1 章：输入数据有哪些合法构造？每种构造对应哪个程序分支？递归调用为什么可以只处理更小的部分？它们随后会成为写解释器、检查器和转换器的共同方法。

原书习题 0.1：给语言特性找正例和反例

习题 0.1 ★ · 让“有些语言……”成为可核查的比较

原书题目

Preface · Usage，p.xix / PDF 20；序言唯一编号习题，无编号小问。

We often use phrases like “some languages have property X.” For each such phrase, find one or more languages that have the property and one or more languages that do not have the property. Feel free to ferret out this information from any descriptive book on programming languages (say Scott (2005), Sebesta (2007), or Pratt & Zelkowitz (2001)).

完整译义：我们经常使用“有些语言具有性质 X”这样的说法。对每一处这样的说法，找出一种或多种具有该性质的语言，再找出一种或多种不具有该性质的语言。可以从任何介绍程序设计语言的书中寻找这些信息，例如 Scott（2005）、Sebesta（2007），或 Pratt 与 Zelkowitz（2001）。

第一组：在 PROC 中，proc (x) x 求值得到一个过程，可以把它绑定给变量、传入另一个过程或作为返回值。LET 的值域只有整数和布尔值，语法中也没有过程构造。因此反例的依据是这门小语言的定义，而不是“暂时没有使用过程”。

第二组：EXPLICIT-REFS 的 newref(0) 返回引用，引用可存到变量里再传递。IMPLICIT-REFS 的变量确实关联存储位置，但引用属于绑定值 DenVal，普通表达式返回的 ExpVal 不包含引用。这里比较的是“能否把引用作为表达式值操作”，不能把结论改说成“IMPLICIT-REFS 没有存储”。

第三组：考虑下面的区分程序。过程体根本不使用 x；但实参若被求值，会尝试把过程值与整数相减。

let f = proc (x) 11
in (f -(proc (y) y, 1))

按值规则在进入过程体前求实参，因此报告非数值减法错误。按需规则先保存待求值表达式和环境；体内没有读取 x，所以不会触发它，结果为 11。这是对原书规则的推演，本批 Python 模型只实现按值求值，没有执行这个按需语言实验。带副作用时还须继续区分按名反复求值与按需缓存。

第四组：INFERRED 可以写 proc (x : ?) -(x,1)，差运算给出 x 必须为 int 的约束，从而推得 int → int。CHECKED 的形式参数处需要写出 int。不能把这组差异概括为“CHECKED 完全不会推导任何表达式的类型”：它同样会按规则计算子表达式和整个表达式的类型，差异在于这里是否允许缺省注解。

对真实语言做同样比较时，还应标明版本、方言与具体构造，并给出最小区分程序。例如一句“这个语言是惰性的”往往不够精确，应该说清是过程实参、局部绑定还是某种容器按需计算。题目所列的参考书提供进一步查找的方向；本解答的四组结论直接依据本版 EOPL，不把未查阅的外部书目列为已核验来源。
